## #task[HuskyLens 循跡模組除錯] 啟動 Cocoya 時的 `Input "RESULT" doesn't exist on "py_ai_get_line_end"`

### 症狀（使用者回報）
```
workspace.js:349 [Workspace] Sync Code Update failed: ReferenceError: Input "RESULT" doesn't exist on "py_ai_get_line_end"
```
啟動 Cocoya 時出現（`workspace.js:349` 為 `triggerCodeUpdateSync` 的 catch，代表 `Blockly.Python.workspaceToCode` 拋錯）。

### 診斷過程（證據鏈）
1. **錯誤訊息語意**：`ReferenceError: Input "..." doesn't exist on "<type>"` 出自 Blockly 12.3.1 `valueToCode()`（`ui/blockly/core/blockly.js`）→ 意即「該積木**實例**沒有名為 `RESULT` 的 input」。而 input 只由 `init()` 產生 → 只能是「建立當下型別未註冊」或「`init()` 提前拋錯」。
2. **但產生器存在**：錯誤來自 `Blockly.Python.forBlock['py_ai_get_line_end']` 被呼叫 → 該產生器（PC 專屬 `ai_inference` 模組）已註冊。**積木未註冊、產生器已註冊**＝兩者在「建立積木」與「產碼」之間被分開載入。
3. **模組依平台載入**：`ui/src/core_manifest.json` 標記 `ai_inference.platforms = ["PC"]`、`mcu_*` 為 `["MicroPython"]`；`module_loader.loadModules` 以平台過濾。未載入型別 `Blockly.Blocks[type] === undefined` → Blockly 只 `console.warn('Block definiton for xxx not found.')` 後建立**空積木**（無 input/field），**不拋錯**（延後到產碼才爆）。
4. **找到順序顛倒的兩個還原入口**（本次真正根因）：
   - `ui/src/app/persistence.js::checkAutoBackup`（啟動備份／專案旁 `.bak` 還原）：`domToWorkspace(...)` **先**、`setPlatformUI(platform)` **後**（且未 await）。
   - `ui/src/app/lifecycle.js::_restoreReloadSnapshot`（換主題／語系 reload 快照）：平台不符時**只 console.warn**，完全不切換。
   （`loadWorkspace` 是正確樣板：先 `setPlatformUI` 再 `domToWorkspace`。）
5. **實機環境佐證**：
   - `%LOCALAPPDATA%\com.cocoya.app\EBWebView\Default\Local Storage\leveldb\000004.log`（Tauri WebView2）內 `cocoya_platform` 值在 `MicroPython`／`PC` 間交錯，且有 **3 個不同 origin**（`http://localhost:5173`、`http://tauri.localhost`、另一 vite port）→ localStorage **依 origin 隔離**，`currentPlatform` 可能與備份 XML 的 platform 不同（預設值為 `MicroPython`，見 `config.js`）。
   - `%TEMP%\cocoya_tauri\` 已無 `untitled_backup_*.xml` → 與「使用者按下『恢復』後 `clearBackup` 已刪除備份」一致（錯誤正是在那次還原後產生）。

### 根因（一句話）
啟動備份／reload 快照的還原流程「**先載入積木、後切換平台**」，導致 PC 專案的 `py_ai_*` 積木在 MicroPython 平台下被建成空積木；隨後 `setPlatformUI('PC')` 註冊了產生器，`triggerCodeUpdate()` 產碼時就爆在 `valueToCode('RESULT')`。

### 技術深挖 (Technical Deep Dive)
- **「空積木」為何是延遲引信**：`Workspace.newBlock()` 對未註冊型別不拋錯（只 warn 後建空積木）。因此錯誤現場（`valueToCode`）與犯案現場（建立積木的那一刻）**時間上分離**，且 console 只有一行不顯眼的 `Block definiton for ... not found`——這是本次最耗時的盲點。判準很簡單：**`Blockly.Blocks[type]` 是否存在**＝該型別在「當下」有沒有註冊；`Blockly.Python.forBlock[type]` 是另一張表，兩者可以不同步。
- **`jsonInit` 的另一條「半成品空積木」路徑**（未來若再遇到同型錯誤要先查）：`argsN` 存在但 `messageN` 未定義時，`jsonInit` 在**附加任何 input 之前**就 throw（`args0 must have a corresponding message (message0).`）；`interpolate → validateTokens` 亦會因 `%N` 超出 `argsN` 長度而 throw（`Message index %N out of range`）。兩者都發生在 i18n 載入順序錯或文案佔位數與 args 不對齊時——所以**模組 i18n 必須先於 `*_blocks.js` 載入**（`module_loader.loadModule` 目前即為此順序，勿調換）。
- **`currentPlatform` 的真實來源**：`localStorage['cocoya_platform'] || 'MicroPython'`（預設 MicroPython）；localStorage **依 origin 隔離**（vite dev `localhost:5173` 與打包 `tauri.localhost` 各自獨立），且多視窗共用同一份 → 「同一台機器上，不同啟動方式／不同視窗可以有不同平台」。任何來自**檔案**（備份/`.bak`/快照）的平台資訊都必須以檔案內容為準，不能沿用記憶體狀態。
- **診斷手法（可重用）**：WebView2 的 localStorage 可直接在 LevelDB 檔（`%LOCALAPPDATA%\com.cocoya.app\EBWebView\Default\Local Storage\leveldb\*.log`）以 UTF-8 grep 出歷史值；App 執行中該檔被鎖，需以 `FileShare::ReadWrite` 共享模式開啟（PowerShell：`[System.IO.File]::Open(path, 'Open', 'Read', 'ReadWrite')`）。這是本次確認「平台與備份不符」的關鍵證據。
- **修法的取捨**：`ensurePlatformForXml` 放在 persistence.js 並以公開名（非 `_`）暴露，因為它是**跨檔共用守門**（lifecycle 也需要）；同時刻意**不**去動 `loadWorkspace`（已是正確樣板）與 `triggerCodeUpdate`（不靜默吞錯），只在 catch 做「訊息降噪」，避免遮蔽真正的產生器契約錯誤。
- **為何不直接「載入 XML 後重建全部積木」**：重建需重跑 toolbox 載入與工作區重建，會丟失 undo/註解/位置等狀態；改用「先切平台」這條最小副作用路徑即根治。

### 真正根因（最終版）
- `ai_inference/i18n/zh-hant.js` / `en.js` 的 `AI_GET_LINE_END` 訊息缺 `%1`，但 `py_ai_get_line_end` 的 `args0` 有 **2 個 arg**（`input_value RESULT`＋`field_dropdown END`，見 `ai_inference_blocks.js:271`）。→ 該型別**任何時候**執行 `init()` 都拋 `Message does not reference all 2 arg(s)`，積木一律變成「半成品空積木」（無 input／field）→ 還原/開檔後產碼即爆 `Input "RESULT" doesn't exist`。**與平台切換無關**（Round 1 是同症狀的另一條潛在路徑，防護保留）。
- 「修了卻沒生效」的第二層：vite dev server 常駐＋`module_loader.loadScript` 的 `script[src]` 去重與 HTTP cache → i18n 修正後 reload 仍載到舊檔。已加 `?_v=<__bootedAt>` cache-busting（`lifecycle.js` 新增 `__bootedAt` 戳記，同一頁面生命週期固定）。

- **同症狀、雙病因**：`Input "X" doesn't exist` 只是「空積木」的下游症狀。病因 A＝建立當下型別未註冊（平台順序）；病因 B＝`init()` 內 `jsonInit` 拋錯（i18n 佔位符與 `argsN` 不對齊）。分辨準則：`Message does not reference all N arg(s)`／`args0 must have a corresponding message` ＝ 病因 B。Round 1 我押了 A（有真實潛在缺陷但非本案兇手），直到 trap 沒響＋repair 拋 B 才扭轉方向——**取證工具（trap/repair）比推理更可靠**。
