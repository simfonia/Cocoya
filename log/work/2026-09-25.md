## #task[MCU serial高頻寫入] MCU 高頻 Serial 輸出穩定性優化

### 背景與觸發情境
在 MCU 模式下，當使用者上傳如：
```python
while True:
    print("hello")
```
的程式碼時，裝置透過 USB Serial 向 PC 發送極高頻率的資料流。在舊版架構下，這會導致：
1. **Python Monitor 同步磁碟 I/O**：`resources/deploy/base.py` 每一批次讀取都同步 `open("...raw_dump.log", "a")`、`write()`、`close()`，嚴重卡死讀取主迴圈並造成大量 CPU 浪費。
2. **Tauri IPC 事件洪水**：Rust 端 reader thread 只要讀到 chunk 就發出 `emit_to("python-log")`，每秒發送數百至數千次 IPC 事件，造成 WebView 事件佇列飽和與記憶體飆升。
3. **前端 DOM 頻繁 Reflow**：`terminal.js` 的 `appendTerminal` 在每個事件觸發時直接操作 DOM、計算 `scrollHeight` 並自動捲動，主執行緒被頻繁 layout 阻塞導致介面停止回應。
4. **資源競爭與 COM 埠無法再次上傳**：`stop_serial_monitor` 僅呼叫 `child.kill()` 而未等待 child 完全退出，Windows 串列埠 handle 未釋放就立即發起新部署，產生 `AccessDenied`，且視窗重新聚焦時會搶先自動重開 monitor。

### 修改清單（依計畫 McuSerialHighFrequencyOutput.md）
1. **Phase 1：raw dump 開發旗標化 (`resources/deploy/base.py`)**
   - 移除在主迴圈內逐批同步開關檔案的舊實作。
   - 新增 `_RawDumper` 類別：改由環境變數 `COCOYA_SERIAL_RAW_DUMP` 明確控制（預設關閉，零額外負擔）；若啟用，以 `queue.Queue(maxsize=1000)` 有界背景線程寫入，隊列滿時安全丟棄並記錄 dropped 計數，退出時優雅 flush。
   - 同步副本至 `src-tauri/target/debug/resources/deploy/base.py`。
2. **Phase 2：Rust 輸出聚合與背壓 (`src-tauri/src/commands/mcu.rs`)**
   - 抽出 `forward_stream_with_backpressure` 通用流轉發函式。
   - 採用有界 channel（最多 128 chunks，約 128KB），reader thread 快速清空 pipe 防止 Python 子進程卡死。
   - 以 30ms 時間窗或 4KB 批次累積發送 IPC 事件（降低 95% 以上 IPC 負擔）；低頻時保持 30ms 內即時發送，維持互動體驗。
   - 若發生背壓超量，普通 log 丟棄並累計 dropped bytes，並在下一批日誌開頭注入 `[Cocoya Warning: 序列埠輸出過於頻繁，已略過約 X KB 日誌]`。
   - 維持多視窗單播契約（`emit_to`）。
3. **Phase 3：前端批次渲染 (`ui/src/ui/terminal.js`)**
   - 實作內部有界隊列 `_terminalQueue`（上限 600）與 `requestAnimationFrame` 排程 flush。
   - 單次 flush 使用 `DocumentFragment` 批次寫入，單次結尾更新 `scrollTop`。
   - 隊列飽和時安全丟棄普通 `out` 訊息並注入警告，報錯與重要控制訊息（`err`/`info`/`success`）永遠保留。
   - 增加單一節點長度保護（`MAX_SPAN_TEXT_LEN = 20000`），避免單一 span 過大卡死瀏覽器繪製。
   - 新增 `appendTerminalBatch(items)` 與手動 `flushTerminal()` 方法。
4. **Phase 4：Monitor 停止與上傳交接 (`src-tauri/src/state.rs`, `src-tauri/src/commands/mcu.rs`, `src-tauri/src/lib.rs`)**
   - `SerialMonitorSession` 增加 `stopped: Arc<AtomicBool>`，支援 reader 與轉發迴圈迅速退出。
   - `stop_serial_monitor` 改為可等待函式：以 `kill_tree` 終止進程樹，等待 child exit（上限 1.5 秒），並加入 100ms 驅動冷卻以徹底釋放 COM 埠。
   - `set_window_focus` 增加執行中/部署中守門：若該視窗在 `python_processes` 中已有進程，切換焦點不得搶先自動重開 monitor。
   - 視窗關閉時的清理邏輯一併更新對齊。
5. **Phase 5：VSIX 相容性回歸**
   - 確認 VSIX 端採用 VS Code 原生 Terminal，不受 Tauri IPC 批次影響，共用 `base.py` 的 I/O 改進同步嘉惠 VSIX。

### 技術深挖 (Technical Deep Dive)
- **非同步有界背壓的必要性**：直接在讀取 thread 同步做磁碟寫入或 IPC 發送，會使底層 OS pipe 緩衝區填滿，導致 Python 的 `print()` 遭到阻塞（deadlock）。使用 Reader thread -> Bounded Channel (TrySend) -> Forwarder Thread 的架構，能讓 Reader 永遠以最快速度 drain pipe；當下游來不及消化時以常數時間丟棄並統計，既保證系統不崩潰，又讓使用者明確察覺資訊被略過。
- **Windows Process Tree 與 COM Port Handle 競態**：在 Windows 上，殺死父進程若未遞迴終止子孫進程，或未 `wait()` 進程完全退出，Serial 驅動程式常會持續鎖定 COM 埠數十至數百毫秒。若隨後立即調用部署程式，就會遭遇 `AccessDenied`。透過 `taskkill /F /T` 加上 child wait 與冷卻期，能根本解決部署碰撞。
- **DOM Reflow 集中化**：瀏覽器處理大量個別 span 的 append、textContent 修改與 scrollTop，每次都會觸發 synchronous layout / reflow。利用 requestAnimationFrame 將多筆日誌聚合成單次 DocumentFragment 插入與單次 scrollTop，能將 JS 執行緒 CPU 佔用率降到最低。

### 技術深挖 (Technical Deep Dive)
- **ProjectRoot 是跨平台 SSOT**：Tauri 以視窗 label 查 `current_paths`，VSIX 以 `currentFilePath` 推導；兩端最終都只產生 `<ProjectRoot>/raw_dump.log`，不依賴 Cocoya 安裝位置、目前工作目錄或 `temp_scripts`。
- **設定變更不強制中斷程序**：切換器只影響下一次 MCU 子進程；Tauri 聚焦重取是自動新程序，因此 focus command 會先把最新偏好同步進 `SerialMonitorWant` 再重開。
- **關閉狀態必須反繼承**：若只「不注入」環境變數，Python 仍可能繼承 shell／父程序設定；Tauri 明確設 `0`，VSIX 三種 shell 明確 unset／清空。
- **寫入錯誤不可靜默**：RawDumper 在啟動 worker 前先建立檔案，權限不足或路徑錯誤會立即寫入 stderr，再由既有 Python error 事件顯示到 Cocoya 終端機。
