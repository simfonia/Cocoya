## [已完成] Python 環境設定：安裝流程重構（Rust 專用命令 + modal 內進度 + 安裝中鎖定）

### 問題（使用者回報）
1. 第一次或從首頁開啟環境設定時，**安裝套件的進度訊息跑到首頁背後的虛擬終端機**，看不到。
2. 安裝是**非同步**，**安裝完 modal 不會更新為「已安裝」**。

### 根因診斷（三個獨立問題，不只一個）

| # | 問題 | 證據 |
|---|---|---|
| 1 | **pip 輸出被送到 modal 之外** | Tauri：`tauri.js` 舊 `installModule` → `CocoyaUI.toggleTerminal(true)` + `run_python` → 輸出到主視窗底部 `#terminalArea`（z-index ~1000），而 `#diagnose-modal` 是 **z-index 10050 的全螢幕遮罩** → 終端機整個被蓋住。VSIX：`envOps.ts` 舊 `handleInstallModule` → `createTerminal('Cocoya Environment')` + `terminal.show()` → 輸出跑到 **VS Code 原生終端機**（webview 之外）。 |
| 2 | **完全沒有完成訊號，重檢靠猜** | Tauri：舊流程送出後**根本不重檢**；`run_python` 只回 `Ok(())`，reader thread 讀到 EOF 就結束，**不回 exit code** → modal 永遠停在「○ 未安裝」。VSIX：`setTimeout(() => this.handleCheckEnvironment(), 5000)` — **固定 5 秒**；tensorflow 要 1–3 分鐘 → 5 秒後重檢必然仍是「未安裝」，狀態更新是假的。 |
| 3 | **隱藏 bug：連點 / 無進行中狀態** | 安裝鈕無 disabled。Tauri 舊流程第二次點會再呼叫 `run_python`，而 `run_python` **第一行就是 `stop_python`**（`python.rs:49`）→ 殺掉前一個 pip 進程且無提示；`stop_python` 還會釋放該視窗的 serial monitor（`python.rs:190-191`）→ 在專案中開環境設定裝套件會**誤殺串列監看**。 |

**E4-B 的關鍵理由**：`prevent_close` 是「後端單方面拒絕關閉 + 前端負責放行」架構，只要前端任一環節失效（JS 錯誤、promise 未 resolve、WebView 卡住），視窗就**永久關不掉**。風險不對稱——省下的只是一次誤關（X 在視窗標題列，離 modal 很遠），賠上的是**工作管理員**。故「鎖定」只鎖 modal 內部，**視窗本身永遠關得掉**。

### 技術深挖 (Technical Deep Dive)

**1. `--progress-bar off` 是「在 modal 內顯示進度」可行的關鍵**
pip 預設進度條以 `\r` 原地刷新；逐行讀取會產生大量破碎行、無法作為可讀日誌。關閉後輸出即為乾淨的行式文字，前端才能取「最後一行非空輸出」做為該列的即時摘要。這個小參數讓整個設計簡單了一個量級。

**2. 為什麼新增 Rust command 而非沿用 `run_python`**
`run_python` 有兩個結構性缺陷無法繞過：(a) 開頭 `stop_python` → 殺掉使用者程式 + 釋放 serial monitor（裝套件時的無關副作用）；(b) 不回 exit code。要修 (b) 只能讓 Python 端自己印完成標記再回推 exit code，那是脆弱且難維護的繞道。獨立 command 同時解決兩者，並沿用專案既有 `start_training` 的事件模式。

**3. Waiter 執行緒的鎖策略（避免與 abort 互鎖）**
若把 `Child` 移入 waiter 執行緒呼叫阻塞式 `wait()`，abort 就拿不到 handle 無法 kill；若用 `Arc<Mutex<Child>>` 並在鎖內 `wait()`，abort 會被鎖住直到安裝結束。解法：Child 留在 map，waiter 以 `try_wait()` **輪詢**（250ms），每次只短暫持有鎖。abort 先 `remove` 項目再 kill；waiter 發現項目消失即靜默結束（done 事件由 abort 負責發），避免雙發。

**4. 「鎖定」範圍必須是「安裝進行中」，不是「環境未完成」**
若以「環境未完成」為鎖定條件，**路徑設錯的使用者會被永久鎖在 modal 內無法逃脫**（因為他永遠無法讓環境「完成」）。鎖定只掛在進行中的安裝上，才是可解除的。且必須保留「中止安裝」為永遠可用的逃生口——否則「禁止關閉」就是牢籠。這是「禁止關閉」能成立的前提。

**5. E4-B：為什麼放棄 `prevent_close`**
`prevent_close` 需要前端在合理時間內回應才放行。前端任一環節失效 → 視窗永久關不掉（Bug D 的 `_isClosing` latch 就是真實前例）。因此：(a) 不新增 prevent_close；(b) 修好既有的 z-index/latch；(c) 關窗在 Rust else 分支直接殺 pip（不留孤兒）。**取捨**：非 dirty 情境下按 X 會直接關閉並中止安裝（不跳提示），因為 Rust 只在 dirty 時才 emit `closeRequested`，前端攔不到；這換得「視窗永遠關得掉」這個更重要的保證。

**6. 三條逃逸路徑（E1/E2/E3）為什麼必須擋**
它們不是「關閉 modal」，而是**整個頁面被重載或狀態被洗掉**，後果比關閉更糟——**後端 pip 還在裝，前端卻忘了**：
- E1 Ctrl+R/F5：`lifecycle.js` 攔截 → `handleReloadRequest` → `resetWorkspace` + 回首頁；且自動彈出邏輯會在 900ms 後重呼 `showDiagnoseModal`，把清單重設為「正在檢查…」+ 送 `checkEnvironment` → 舊結果（必然 false）覆蓋 → 看起來像沒在裝。
- E2 語系切換 → `reloadWebview` → **頁面真重載** → `_envInstall` 全失。
- E3 主題切換 → 一律 `reloadWebview` + 800ms fallback `location.reload()` → **註定重載**。

封住三者後，「重開 modal 情境」只剩 E1（同頁，記憶體狀態保留），因此「關閉後再看進度」與「持久顯示進度」兩個需求合而為一。

**7. 純前端停滯偵測的必要性**
後端只在子進程**結束**時發 `install-module-done`；真 hang 住時永遠收不到事件 → 進度橫幅會一直顯示「安裝中」而無限等待。以「無輸出時間」（`lastOutputAt`）分級並用**說明性措辭**（「已 N 秒無新輸出，可能正在編譯或網路較慢」）而非武斷說「卡住」，避免誤判（tensorflow 編譯期本來就可能長時間無輸出）。零後端成本。

**8. 為什麼「失敗不停整批」**
pip 相依問題常見（例如 tensorflow 在 Python 3.13 裝不到）。若第一個失敗就中止，使用者得反覆手動重試 N 次。繼續跑完能**一次暴露所有問題**，符合「讓使用者清楚知道卡在哪」的目標；最後給總結 + 失敗清單。

**9. HTML 轉義（XSS／破版防護）**
套件名與 pip 輸出來自後端，且 `Pillow (Image)` 這類名稱含括號／可能含引號。改為 `_escapeHtml()` + `data-install-id` 事件委派，取代原本的 inline `onclick="...'${mod.name}'..."`（該寫法遇到引號會直接爆掉）。
