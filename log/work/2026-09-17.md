## #task[DM P2 標籤管理UI消失] 兩項實機回報修正（拍照後管理 UI 消失／改名後 tooltip 與 spec 檔名不同步）

### 症狀（使用者回報）
1. **拍照後中欄「標籤管理」UI 消失**：live 影像採集每拍一張，中欄結構面板的標籤管理器（下拉＋新增/編輯/刪除）就不見。
2. **改標籤連動改名**：資料夾與檔名在磁碟上已同步改名（OK），但
   - 右欄縮圖 hover tooltip（title）仍顯示舊檔名；
   - `dataset.json` 的 `samples[].image_path` 只更新了資料夾段、檔名仍為舊值。

### 根因（兩個獨立 bug）

#### Bug 1：`renderLabelStats` 覆寫結構面板 innerHTML（P2 病根漏改兩處）
`ui_layout.js` 的 `addSampleFromSampler()`（拍照落樣本）與 `handleDeleteImage()`（刪圖）仍保留舊寫法：

```js
const structureContent = modal.querySelector('#dataset-structure-content');
if (structureContent) UIComponents.renderLabelStats(structureContent, state.spec.toJSON().stats);
```

P2（2026-09-16）後，`#dataset-structure-content` 內裝的是 `renderStructurePanel()` 產生的
`#view-label-class-manager`（統一標籤管理器）＋ `#view-label-stats`（統計）。
上述覆寫把容器 `innerHTML` 換成「純統計」→ **管理器整塊被蓋掉**；且 `updateStatsFromImages()`
之後的 `renderStatsPanels()` 找不到 `#view-label-stats`，會退回同一容器再覆寫一次，
故直到下次 `refreshDynamicPanels()/renderStructurePanel()` 才復原。
（P2 已修 sampler/feature 兩處，這兩條路徑漏改。）

#### Bug 2a：磁碟 rename 回傳路徑與 `img.diskPath` 分隔符不一致 → 對帳 miss
- 後端（Tauri `file.rs::dataset_rename_label`、VSIX `datasetOps.ts::handleDatasetRenameLabel`）
  回傳的 `oldPath/newPath` 皆有 `replace('\\','/')` 正規化（全正斜線）。
- 而 `img.diskPath` 來自 capture 的 `savePath`：VSIX `path.join(...)`＝**反斜線**；
  Tauri `${projectRoot}/dataset/...`（projectRoot 來自 Rust anchor）亦含**反斜線**。
- 舊碼 `map.has(img.diskPath)` 直接字串比對 → 必然 miss → 落到 else 分支
  「只同步 `img.path` 的目錄段、檔名不動」→ 正是「spec 資料夾新／檔名舊」的觀察結果。

#### Bug 2b：對帳後沒有重繪縮圖
`handleLabelRenamedOnDisk()` 對帳後只呼叫 `refreshPreview()`（更新 JSON/驗證/自動落盤），
未重繪縮圖；而 tooltip 的 `title` 吃 `img.path`（`ui_components.renderImageGrid` L30 /
`renderAnnotationThumbnails` L94）→ hover tip 停留舊值。

### 技術深挖 (Technical Deep Dive)

#### 1. 「統計面板就地更新」與「整塊 innerHTML 覆寫」的差別是本 bug 的關鍵
`#dataset-structure-content` 是**複合容器**（P2 後同時裝管理器與統計），因此任何把
`renderLabelStats(container, ...)` 指向它的呼叫都是危險寫法。正確 SSOT：
- 統計 → 只寫 `#view-label-stats`（`renderStatsPanels()` 優先路徑）；
- 需要重建面板 → `renderStructurePanel()`（重建 `#view-label-class-manager`＋`#view-label-stats`）。
本次在 `renderStatsPanels()` 加了「容器消失但管理器仍在 → 重建面板」的守門條件，
讓「未來任何誤刪統計容器」都不會再造成管理器消失。

#### 2. 為什麼清理舊寫法時要保留 `renderStatsPanels` 的第三分支
表格 file 模式（`projectType !== image/* 且非 live`）的 `#dataset-structure-content` 裝的是
欄位編輯器（`#dataset-column-list`），該模式沒有統計容器；此時 `state.images.length === 0`，
第三分支不會觸發，屬安全殘留（保留可避免改動表格路徑行為）。

#### 3. 路徑比對的正規化責任歸屬
後端已正規化（`replace('\\','/')`）是**單邊**正規化，前端拿到的 `savePath` 未經正規化。
本次把比對責任放在前端純函式內、統一使用 `core/pathPolicy.normalizePath`（既有 SSOT），
避免「一端正規化、一端不比對」的半套契約。另加「basename 唯一兜底」處理
企業/校園常見的「專案複製到不同磁碟或大小寫不同」情境；並以「同名多筆即不兜底」
避免誤改無關檔案。

#### 4. 對帳後必須重繪縮圖，不能只刷新 JSON
`refreshPreview()` 只做 `syncSpecFromUI` + validate + JSON 預覽 + autosave，**不碰縮圖 DOM**。
凡會改動 `img.path / img.label / img.diskPath` 的流程（改名、增刪類別）都必須顯式呼叫
`refreshThumbnailBadges()`；此為 P2 之後的既有契約，本次補上漏掉的呼叫點。

### 技術深挖 (Technical Deep Dive)
- **為什麼不用後端檢查目錄是否存在**：方案 A 要求零後端改動；且「目錄存在」不等於「有內容」（autosave 會建立空目錄只放 dataset.json），以後端存在性判斷反而更容易誤報。改以 state 內兩項**穩定且不會被 autosave 污染**的證據反推：
  - `img.diskPath`（capture 時寫入的絕對路徑；改名不會更新它）→ 尾段 `<標籤>/<檔名>` 反推倒數第三段＝名稱（最精確，且不受「專案根內恰好也有 dataset 目錄」影響）。
  - `state.sourceFolderPath`（file 匯入時設定為 canonical 目錄，改名不會更新）→ 取 `dataset` 段之後一段。
- **反例（為何不用 autosave 回的 path）**：改名後 autosave 立即在新名目錄寫 dataset.json → 該訊號會在改名瞬間變成「新名」，偵測不到漂移。
- **保守失敗模式**：所有取不到證據的情況（非 canonical 形狀、外部資料夾、無 diskPath）一律回 `drifted:false` → 寧可漏提示（影響：多一份 dataset.json）也不要對未落盤的使用者誤報。
- **同組漂移只提示一次**：`nameDriftWarnKey = diskName + "->" + newName`，避免使用者逐鍵輸入時訊息連發；`enterWorkspace`（新會話）與警示解除時重設。

### 症狀

`ui/src/modules/core/logic/toolbox.xml` 檔頭帶 **UTF-8 BOM（EF BB BF）**。BOM 出現在根元素前，DOMParser 視為非法字元 → `filterToolboxXML`（ui/src/utils/toolbox.js）偵測到 parsererror → 整個模組 toolbox 被靜默跳過。全倉 23 個 toolbox.xml 掃描，另發現 `ui/src/modules/ai_inference/toolbox.xml` 同樣帶 BOM（潛在下一顆地雷）。

1. 兩個檔案以 UTF-8 **無 BOM** 重寫（hex 複查檔頭已是 `<category`，全倉掃描無殘留）。
2. 防護補強：`filterToolboxXML()` 開頭 `xmlString = String(xmlString).replace(/^\uFEFF/, '')`——未來任何來源（host 讀檔/快取/使用者編輯器另存帶 BOM）都不會再炸整個模組。

## #task[Function內if縮排] 2空格縮排下函式內 if 不縮排修復（2026-09-17）

### 症狀
2 空格縮排設定下，function 積木內的 if 積木不會縮排（主體與 if 同層，Python 縮排壞掉）；4 空格設定正常；main/while 積木 2/4 皆正常。

### 根因：縮放兩次而塌陷
- `ui/src/utils/generators.js` 的 Global Indent Scaler（finish 攔截器）假設 `definitions_` 內容皆為「基準 4 空白」靜態模板，INDENT≠4 時將行首 4 空白倍數等比縮放成 INDENT。
- 但 `py_function_def` 注入 `definitions_` 的 branch 來自 `statementToCode`，縮排**已套用當前 INDENT**。2 空格設定下 if 主體（2 層=4 空格）被 scaler 誤判為「基準 4 的 1 層」→ 縮成 2 空格 → 與 if 同層。
- 4 空格時 scaler 恆等（targetLen===4 跳過）故正常；main/while 走主流程輸出不經 definitions_ 故不受影響。
- 全倉盤點：其餘數十處 definitions_ 注入皆為寫死 4 空白模板（符合規範），唯一例外即 py_function_def。

### 修正
`ui/src/modules/core/functions/functions_generators.js`：py_function_def 在存入 definitions_ 前，將 branch 行首的當前 INDENT 倍數**還原為基準 4 空白**（regex 逐行換算），空函式 fallback 改 `'    pass\n'`。全 definitions_ 統一基準 4，scaler 於 2/8 空格下皆正確。

### 驗證
- `node --check` PASS；`vite build` PASS（198ms）。
- Node 模擬完整管線（statementToCode → 還原基準 4 → scaler targetLen=2）：def 0 / if 2 / 巢狀 if 4 / print 6 空格，層級正確。

### 下次啟動方向 (Next Steps)
- 待使用者實機：2 空格設定下函式內放 if（含巢狀）產碼檢查縮排；4 空格回歸確認不變。
- 選單/未來規範：任何要寫入 definitions_ 且含 statementToCode 輸出的產生器，必須先還原基準 4 空白（可考慮把還原抽成 CocoyaUtils 共用函式）。

## #task[Examples播種到AppData] Tauri examples 安裝位置與寫入權限解耦（2026-09-17）

### 問題
Tauri 版開啟 examples 會複製副本到桌面，根因是 examples 打包在 Program Files（系統資料夾，無法寫入）。使用者拍板：改為安裝在 AppData（方案 B：first-run seeding），且 ①examples 維持唯讀保護 ②升級只補缺檔，還原範例功能列 backlog。

### 設計
- **播種 (Seeding)**：`setup` hook 呼叫 `utils::ensure_examples_seeded()`——首次啟動/升級時，把 Resource examples 以 `copy_dir_merge`（已存在檔案跳過、只補缺檔）複製到 `app_data_dir()/examples`（%AppData%\com.cocoya.app\examples），並寫入 `.seeded_version` 版本戳記（供未來「還原範例」判斷）。Dev 模式（is_dev_examples_dir）跳過，仍用 repo 原始檔。

## 追加（同日）：關閉重開 Cocoya 後開範例又回到 Program Files — dev 分支誤判

### 症狀（實機回報）
安裝後首次啟動：examples 正確播種到 AppData、開範例引導到複本；關閉重開 Cocoya：開範例對話框又回到 Program Files 的 examples。

### 根因
`get_examples_path()` 的開發模式分支僅以「current_dir/examples 存在」判定。Release 安裝版資源就放在 exe 同目錄（Program Files\Cocoya\examples），且從捷徑啟動時 current_dir＝exe 目錄 → dev 分支命中 → 直接回傳 Program Files examples，AppData seeded 判斷根本沒跑到。首次啟動（從安裝程式啟動、cwd 非 exe 目錄）僥倖未中。

### 修正（`src-tauri/src/utils.rs::get_examples_path`）
1. dev 分支加 `is_dev_examples_dir()`（repo 標記 src-tauri 目錄）守門，與 ensure_examples_seeded 同一準則；dev 判定失敗才走 seeded → Resource。
2. 原最後 fallback 引用的 dev_path 已移入 if 區塊 → 改為 resource_dir()/examples 兜底（resolve 徹底失敗回空路徑）。

### 驗證
- `cargo check` PASS。待實機：捷徑重啟 → 開範例應導向 %AppData%\com.cocoya.app\examples；dev 模式行為不變。
### 教訓
- 「目錄存在」不可作為 dev/release 判據——Release 安裝目錄結構與 repo 同形。is_dev_examples_dir()（src-tauri 標記）是 SSOT，所有 dev/release 分歧點都必須經它守門。
