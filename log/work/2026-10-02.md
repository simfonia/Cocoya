### 2.2 VS Code 深色越權 bug（已提交 `f63d5f0`）

### 2.3 B/C 類 token 化（本次）

#### 2.3.1 問題定義：不是「難看」，是「不可達」

`theme_manager.js:8` 宣稱「自訂主題只需 `registerTheme({id, cssVars, blockly})` 即插即用」，
但 dark 覆寫規則直接寫**字面值**，而 `theme_manager.js:179` 是把 cssVars 寫在 **body 行內樣式**
—— 字面值不會被 cssVars 覆蓋，故新主題作者對這一塊的顏色**完全摸不到**。

#### 2.3.2 核心手法：把「dark 覆寫」換成「雙主題 token」

以 focus ring 為例（本日最大宗的一類）：

```css
/* 舊：light 規則用一個 token、dark 覆寫換成另一個 token */
.dataset-source-panel input:focus { box-shadow: 0 0 0 2px var(--dsm-brand-soft); }
body.vscode-dark … input:focus, body.cocoya-dark-mode … input:focus { box-shadow: 0 0 0 2px var(--dsm-brand-strong); }

/* 新：單一規則 ＋ 主題感知 token，dark 覆寫整組刪除 */
.dataset-source-panel input:focus { box-shadow: 0 0 0 2px var(--dsm-focus-ring); }
```

**關鍵發現**：`--dsm-brand-soft`（`rgba(254,47,137,0.15)`）與 `--dsm-brand-strong`（`rgba(254,47,137,0.3)`）
在三主題的值**完全相同** —— 這個 dark 覆寫從來不是「主題差異」，而是
「深色底需要更明顯的 focus ring」。既然如此，正確的表達方式就是**一個主題感知 token**，
而非「CSS 層的 dark 覆寫」。新 token `--dsm-focus-ring` ＝ light `0.15`／dark `0.3`／candy `0.3`。

## 3. 技術深挖 (Technical Deep Dive)

### 3.1 踩坑 ①：CSS 註解裡的 glob 讓整份樣式表解析異常，而所有測試都是綠的

我在 `dataset_manager.css` 檔頭註解裡寫了 glob（`src` 後接兩層斜線再接副檔名）。
其中的「星號＋斜線」兩字元序列被 CSS 解析器當成**註解結束符** → 檔頭註解提前中斷 →
後文被當選擇器解析 → VS Code 報「L44 必須是左大括號」「L52 預期為 at-rule 或選取器」。

- **同一個錯誤在 `.mjs` 的 JSDoc 註解裡重演一次**：我為了記錄這件事而寫的說明文字本身就含該序列
  → `dataset_theme_contract.test.mjs` 當場語法錯誤（`node --check` 報 `Invalid regular expression`）。
- **CSS 與 JS 的註解是同一個陷阱**，且寫說明時特別容易再犯（要描述那個 glob 就得寫出那個 glob）。
  凡需舉例一律改用「星號＋斜線序列」這類描述性文字，**不寫字面**。
- **為什麼測試全綠**：CSS 語法錯誤只有 `vite build`（lightningcss）會抓，而
  `npm test` = `test:unit`（compile ＋ lint ＋ lint:ui，只掃 `.js/.mjs`）＋ `test:ui`
  → **不含 `vite build`、也不含 `.css`**。JS 側已被 eslint 完整覆蓋（實測：區塊註解提前閉合 →
  eslint 立刻報 Parsing error），故這道守門**只針對 CSS**，為 JS 再造一份只是重複造輪子。

### 3.2 踩坑 ②：A 類變異測試兩次失敗 —— 抓到「假安全感」

| # | 破壞方式 | 預期 | 實際 |
|---|---|---|---|
| ① | 刪 dark 規則時刪除範圍從 `{` 行起算 | 自檢報紅 | ❌ **報「自檢通過」並寫入壞 CSS** |
| ② | 守門 5 的 `parseRules` 把 `selStart` 設在 `{` 之後 | 抓到冗餘 | ❌ **靜默回傳空 = 假綠** |
| ③ | 守門 5 的 light map 只留**第一條**同名規則 | 抓到冗餘 | ❌ **漏放**（自檢報紅才發現） |

- **根因①的更關鍵體認**：選擇器跨多行時只刪 `{` 行起算會留下裸選擇器行，
  但**裸選擇器行在語法上是合法的** —— 它會被「下一條規則的選擇器」接續起來，
  只是讓該元素在 dark 下多吃到一條不該有的規則（靜默視覺回歸）。
  故「大括號平衡」「sel 是否以逗號結尾」等**語法層自檢都抓不到**，判準只能落在語意上。
- **根因②③**：寫守門時複製了有 bug 的解析器。選擇器在 `{` **之前**；
  且規則是在 `}` 分支 push，`sel` 必須 `slice(selStart, openIdx)`。

## 6. 追加任務：DM P3 標註尺規 bug（2026-10-02）

**現象（使用者回報）**：滑鼠不在影像上時，十字尺規仍然顯示，甚至黏在影像邊緣不消失。

**真因**（`ui/src/modules/dataset_manager/ui_canvas.js::bindEvents()`）：
1. `mousemove` 掛在 **`window`**（為了拉框拖出畫布時仍能追蹤座標），不是掛在 canvas；
   `canvas.mouseleave` 只能在「離開畫布那一刻」清除一次。
2. handler 內座標先被 `clamp(e.clientX - rect.left, canvas.width)` 釘進 `[0, w]`／`[0, h]`，
   於是「影像外」的滑鼠位置會被換算成「貼著邊界」的座標 → `pointerX/pointerY` 永遠有值。
3. 兩者相乘：`mouseleave` 把 pointer 清成 `null` → 下一次任意 window `mousemove` 又立刻設回邊界值
   → 尺規等於清不掉，`drawCrosshair()` 的 `pointerX === null` 守門形同虛設。

**修正**：座標拆成未 clamp 的 `rawX/rawY`（判定是否真的在影像上）與 clamp 後的 `currX/currY`
（拉框、line 模式橡皮筋仍需邊界值）。bbox 分支改為 `pointerX = inside ? currX : null`，
`inside` 以 raw 座標對 `canvas.width/height` 比對：
- 影像外 → 收起尺規（含拉框拖出畫布：尺規跟著收；預覽框 `currentBbox` 仍用 clamp 座標，行為不變）。
- 影像內 → 與原行為完全一致。`mouseleave` 保留（可即時收起，不必等下一次 mousemove）。

**測試**（`ui_canvas.test.mjs` 28 → 30 例，全量 282 → 284）：
- `游標在影像外的 window mousemove 不得設定 pointer（尺規黏邊）`：左側（x=-40）／下方（y=700）出界皆須 `null`。
- `mouseleave 清除後，影像外的 window mousemove 不得把尺規設回來`：影像內追蹤 → mouseleave → 再出界 →
  必須仍為 `null`，且清空呼叫紀錄後重繪不得再呼叫 `setLineDash`。
- 順帶補齊 `setupCanvas()` 的**拉框狀態重置**（`isDrawing/drawingState/startX/startY`）：同檔測試共用 `UICanvas.state`，
  前一個測試殘留的 `isDrawing=true` 會讓後一個測試憑空長出預覽框，而**預覽框的虛線外框也呼叫 `setLineDash`**
  → 讓「尺規是否繪製」的斷言誤判（本次實測踩到 30→29 的假紅，故一併補齊並在前置條件斷言）。

**變異測試**：把兩行改回 `= currX / = currY` → 新增 2 測立即變紅（28 pass / 2 fail）；還原 → 30/30 綠。

## 12. 行尾（LF/CRLF）問題根治（2026-10-03）

**使用者提問**：為何還是常常發生 LF/CRLF 問題？→ 實測盤點 + 建立三層防護。

### 12.1 診斷：為何 .gitattributes 不夠

`.gitattributes` 的 `* text=auto eol=crlf` **只在經過 git 的路徑生效**（checkout / add / diff）。
但編輯器、Python 腳本、PowerShell **直接寫檔不經過 git**，工作區就會變成 LF。

**關鍵：git 偵測不到。** `git status` 把「工作區 LF + 轉換後 LF」視為無差異 →
問題不會自己浮現，會靜態累積。

**實測現況**：646 個文字檔中 **126 個工作區是 LF**，含
`ui/src/bridge/tauri.js`(1860 行)、`resources/dataset_manager/dataset_sidecar.py`(1197 行)、
`package.json`、`tsconfig.json` 等核心檔案；另有 25 個**混合行尾**
（同一檔案內 CRLF/LF 並存，危害最大）。

### 12.2 三層防護（本次建立）

| 層 | 機制 | 作用 |
| --- | --- | --- |
| 1 預防 | `.editorconfig`（新建） | 編輯器存檔當下就寫對，不需經過 git |
| 2 保險 | `.gitattributes`（既有） | git 取出時轉換 |
| 3 驗證 | `scripts/eol.cjs`（新建）+ `npm run eol:check/fix` | CI／手動驗證與修復 |

**已接入 `npm run test:unit` 末段** → `npm test` 會擋，不再靠記憶。

### 12.3 工具自我驗證機制（重要設計）

`scripts/eol.cjs` 內含 `verifyAgainstGit()`：以 `git ls-files --eol` 交叉比對，
列出「git 認定工作區是 LF、但本工具沒掃到」的檔案。

**為什麼需要**：若沒有這道，工具漏抓時會**自以為全綠**（假安全感）。
實作當天即靠它抓出三個漏網：
- `ui/.eslintrc.json`（basename 以 `.` 開頭**但有副檔名**，原判斷誤以為已涵蓋）
- `src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`（原 SCAN_DIRS 沒掃 `src-tauri/` 根）
- `esp32s3_flash`（**無副檔名**的 esptool shell 腳本）

### 12.4 修復結果

- 首次 `--fix`：143 檔（含 25 混合行尾）；補漏後再修 6＋1 檔。
- **最終 `git ls-files --eol` 僅剩 2 個 vendored 檔為 LF**
  （`highlight.min.js` / `python.min.js`，`.gitattributes` 已標 `-text`，刻意排除）。
- 614 個受檢查文字檔全數 CRLF。

### 12.5 教訓

- **「git 不報錯」不等於「沒問題」**：行尾是最典型的例子 —— 工具層（git）看不見，
  只有檔案系統層才看得到。故必須有一個**獨立於 git 的驗證工具**。
- **守門工具要有自我驗證**：任何「掃描型守門」都可能漏抓；讓它與另一個獨立來源
  （此處是 git 的 `ls-files --eol`）交叉比對，才能避免假安全感。
  這是 AGENTS.md「掃描型守門不可過度寬泛」的延伸：**也要確認不過度狹窄**。

### 12.6 驗收

| 項目 | 結果 |
| --- | --- |
| `node scripts/eol.cjs` | ✓ 614 檔全 CRLF，交叉比對無漏網 |
| 守門變異測試 | 手動造 LF 檔 → exit 1 並指出檔案；混合行尾 → 正確偵測並修復 |

## 13. 行尾危害的實測澄清（2026-10-03）

**使用者提問**：「不理它對程式有影響嗎？為何一定要用 CRLF？」
→ 實測後**修正了第 12 節過度強調的說法**。

### 13.1 實測：對「程式執行」幾乎沒有影響

| 實測 | 結果 |
| --- | --- |
| CRLF 檔執行 | `('42', 0)` |
| LF 檔執行 | `('42', 0)` —— **完全相同** |
| CRLF 檔的多行字串 | `'line1\nline2'` —— **不含 `\r`** |
| LF 檔的多行字串 | `'line1\nline2'` |

Python/JS/Rust 的解析器會自動正規化行尾。**「一定要 CRLF」這個說法本身不精確**：
真正必須的是「全專案一致」，CRLF 只是本專案（Windows）選定的基準。

### 13.2 真正的危害在「用工具改檔」

```
naive split(b'\n') 讀 CRLF 檔 -> [b'x\r', b'y\r', b'z\r', b'']   # 每行尾巴殘留 \r
naive split(b'\n') 讀 LF   檔 -> [b'x',   b'y',   b'z',   b'']
git：內容一字未改、只換行尾 -> status 仍顯示 'M a.txt'（假變更，污染 diff）
```

這些殘留的 `\r` 會導致：① 寫回時產生**混合行尾** ② 正則/內容比對失配
③ 統計 off-by-one、hash 不符。

### 13.3 判準修正：危害排序

> **混合行尾 > 純 LF 或純 CRLF 不一致 > 統一使用哪一種**

混合行尾會讓同一檔案內不同行的行為不一致，才是我們要優先杜絕的；
純 LF 檔只是「一致性偏好」，不是 bug。

### 13.4 據此調整的實作

1. **AGENTS.md**：新增「⚠️ 先釐清」段落，用實測數據說明對程式執行無影響，
   並明列危害排序；把「必須 CRLF」改為「必須一致，CRLF 是選定基準」。
2. **`scripts/eol.cjs`**：`--list` 與檢查模式**依危害分級輸出**——
   混合行尾優先列出並標註「危害最大」，純 LF 標註「對程式執行無影響，屬一致性問題」。
   （實作時踩坑：用編輯器改這段因行尾差異匹配失敗，改用行號切片重寫才成功。）

### 13.5 驗收

守門正常（614 檔全 CRLF）、危害分級輸出經探測檔驗證（混合+純 LF 各一，
前者被優先顯示）、全專案 292/292 綠、lint 0 error。
