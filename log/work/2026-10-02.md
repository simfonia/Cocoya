### 2.2 VS Code 深色越權 bug（已提交 `f63d5f0`）

### 2.3 B/C 類 token 化（本次）

#### 2.3.1 問題定義：不是「難看」，是「不可達」

`theme_manager.js:8` 宣稱「自訂主題只需 `registerTheme({id, cssVars, blockly})` 即插即用」，
但 dark 覆寫規則直接寫**字面值**，而 `theme_manager.js:179` 是把 cssVars 寫在 **body 行內樣式**
—— 字面值不會被 cssVars 覆蓋，故新主題作者對這一塊的顏色**完全摸不到**。

#### 2.3.2 核心手法：把「dark 覆寫」換成「雙主題 token」

以 focus ring 為例（本日最大宗的一類）：

```css
/* 舊：light 規則用一個 token、dark 覆寫換成另一個 token */
.dataset-source-panel input:focus { box-shadow: 0 0 0 2px var(--dsm-brand-soft); }
body.vscode-dark … input:focus, body.cocoya-dark-mode … input:focus { box-shadow: 0 0 0 2px var(--dsm-brand-strong); }

/* 新：單一規則 ＋ 主題感知 token，dark 覆寫整組刪除 */
.dataset-source-panel input:focus { box-shadow: 0 0 0 2px var(--dsm-focus-ring); }
```

**關鍵發現**：`--dsm-brand-soft`（`rgba(254,47,137,0.15)`）與 `--dsm-brand-strong`（`rgba(254,47,137,0.3)`）
在三主題的值**完全相同** —— 這個 dark 覆寫從來不是「主題差異」，而是
「深色底需要更明顯的 focus ring」。既然如此，正確的表達方式就是**一個主題感知 token**，
而非「CSS 層的 dark 覆寫」。新 token `--dsm-focus-ring` ＝ light `0.15`／dark `0.3`／candy `0.3`。

## 3. 技術深挖 (Technical Deep Dive)

### 3.1 踩坑 ①：CSS 註解裡的 glob 讓整份樣式表解析異常，而所有測試都是綠的

我在 `dataset_manager.css` 檔頭註解裡寫了 glob（`src` 後接兩層斜線再接副檔名）。
其中的「星號＋斜線」兩字元序列被 CSS 解析器當成**註解結束符** → 檔頭註解提前中斷 →
後文被當選擇器解析 → VS Code 報「L44 必須是左大括號」「L52 預期為 at-rule 或選取器」。

- **同一個錯誤在 `.mjs` 的 JSDoc 註解裡重演一次**：我為了記錄這件事而寫的說明文字本身就含該序列
  → `dataset_theme_contract.test.mjs` 當場語法錯誤（`node --check` 報 `Invalid regular expression`）。
- **CSS 與 JS 的註解是同一個陷阱**，且寫說明時特別容易再犯（要描述那個 glob 就得寫出那個 glob）。
  凡需舉例一律改用「星號＋斜線序列」這類描述性文字，**不寫字面**。
- **為什麼測試全綠**：CSS 語法錯誤只有 `vite build`（lightningcss）會抓，而
  `npm test` = `test:unit`（compile ＋ lint ＋ lint:ui，只掃 `.js/.mjs`）＋ `test:ui`
  → **不含 `vite build`、也不含 `.css`**。JS 側已被 eslint 完整覆蓋（實測：區塊註解提前閉合 →
  eslint 立刻報 Parsing error），故這道守門**只針對 CSS**，為 JS 再造一份只是重複造輪子。

### 3.2 踩坑 ②：A 類變異測試兩次失敗 —— 抓到「假安全感」

| # | 破壞方式 | 預期 | 實際 |
|---|---|---|---|
| ① | 刪 dark 規則時刪除範圍從 `{` 行起算 | 自檢報紅 | ❌ **報「自檢通過」並寫入壞 CSS** |
| ② | 守門 5 的 `parseRules` 把 `selStart` 設在 `{` 之後 | 抓到冗餘 | ❌ **靜默回傳空 = 假綠** |
| ③ | 守門 5 的 light map 只留**第一條**同名規則 | 抓到冗餘 | ❌ **漏放**（自檢報紅才發現） |

- **根因①的更關鍵體認**：選擇器跨多行時只刪 `{` 行起算會留下裸選擇器行，
  但**裸選擇器行在語法上是合法的** —— 它會被「下一條規則的選擇器」接續起來，
  只是讓該元素在 dark 下多吃到一條不該有的規則（靜默視覺回歸）。
  故「大括號平衡」「sel 是否以逗號結尾」等**語法層自檢都抓不到**，判準只能落在語意上。
- **根因②③**：寫守門時複製了有 bug 的解析器。選擇器在 `{` **之前**；
  且規則是在 `}` 分支 push，`sel` 必須 `slice(selStart, openIdx)`。

## 6. 追加任務：DM P3 標註尺規 bug（2026-10-02）

**現象（使用者回報）**：滑鼠不在影像上時，十字尺規仍然顯示，甚至黏在影像邊緣不消失。

**真因**（`ui/src/modules/dataset_manager/ui_canvas.js::bindEvents()`）：
1. `mousemove` 掛在 **`window`**（為了拉框拖出畫布時仍能追蹤座標），不是掛在 canvas；
   `canvas.mouseleave` 只能在「離開畫布那一刻」清除一次。
2. handler 內座標先被 `clamp(e.clientX - rect.left, canvas.width)` 釘進 `[0, w]`／`[0, h]`，
   於是「影像外」的滑鼠位置會被換算成「貼著邊界」的座標 → `pointerX/pointerY` 永遠有值。
3. 兩者相乘：`mouseleave` 把 pointer 清成 `null` → 下一次任意 window `mousemove` 又立刻設回邊界值
   → 尺規等於清不掉，`drawCrosshair()` 的 `pointerX === null` 守門形同虛設。

**修正**：座標拆成未 clamp 的 `rawX/rawY`（判定是否真的在影像上）與 clamp 後的 `currX/currY`
（拉框、line 模式橡皮筋仍需邊界值）。bbox 分支改為 `pointerX = inside ? currX : null`，
`inside` 以 raw 座標對 `canvas.width/height` 比對：
- 影像外 → 收起尺規（含拉框拖出畫布：尺規跟著收；預覽框 `currentBbox` 仍用 clamp 座標，行為不變）。
- 影像內 → 與原行為完全一致。`mouseleave` 保留（可即時收起，不必等下一次 mousemove）。
