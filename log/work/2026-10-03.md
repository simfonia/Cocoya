# Cocoya 工作日誌 2026-10-03

## 1. P1-5：移除 sidecar 自動 pip install paramiko（安全）

### 1.1 原始缺陷

`resources/dataset_manager/dataset_sidecar.py` 於 **module level**（import 時即執行）：

```python
try:
    import paramiko
except ImportError:
    subprocess.check_call([sys.executable, "-m", "pip", "install", "paramiko"], **_POPEN)
```

風險三項（計畫 §3 P1-5）：
1. **未告知使用者即修改全域 Python 環境** —— sidecar 一被啟動就可能觸發，與「使用者按了安裝按鈕」完全無關。
2. **離線環境必失敗**（`check_call` 丟例外，只印 log 後繼續，實際上 paramiko 仍缺）。
3. **可能觸及權限提升**（裝到系統 Python 時）。

且舊碼**已有降級路徑卻形同虛設**：4 個使用點（`checkRemoteEnvironment`／`uploadDataset`／`trainRemote`／`stopTraining`）
各自寫了 `except ImportError` 與中文文案，但因為 module level 已 pip 安裝過，這些分支平時根本不會走到
—— 屬「錯誤處理寫了但不可達」，與 G2 serial 的死碼同類病根。

### 1.2 修法（選項 1：純降級回報錯誤碼）

依計畫首選，不做「使用者同意開關」（該選項需新增設定偏好＋pip 指向 venv，收益僅在使用者確實想用
遠端訓練時才吃得到；本專案遠端訓練僅在 `py_ai_train_run(backend='remote')` 觸發，頻率低，
純降級＋明確安裝指引已足夠）。

**sidecar**
- 刪除 module level 的 `import paramiko` + `pip install` 整段。
- 新增 `PARAMIKO_MISSING = "SSH_PARAMIKO_MISSING"` 與 `_require_paramiko() -> (module, errorCode)`。
- 4 個使用點改走 helper，缺裝時回 `{"errorCode": "SSH_PARAMIKO_MISSING", "error": "paramiko not installed"}`
  （`error` 僅為除錯用，**不再放展示文案**，符合 AGENTS.md「錯誤碼後端定義、文案前端 i18n」）。
- `stopTraining` 順帶修正一個舊缺陷：原 `do_stop` 的 paramiko 匯入在 `try` 內且**無 `except ImportError`**，
  缺裝時會被外層 `except Exception` 吞成「中斷失敗: name 'paramiko' is not defined」；現明確分流，
  且補 `self._remote_train = None`（原本 `finally` 才清，缺裝早退會讓訓練狀態卡住，之後無法再「中斷」）。

**前端 / Host（i18n 與透傳）**
- `ui/src/zh-hant.js` / `en.js` 新增 `MSG_PARAMIKO_MISSING`（指引：Python 環境設定面板或終端機 pip）。
- `ui/src/bridge/tauri.js`：`startRemoteTraining` 的 `trainingError`、`datasetUploadArchive` 的
  `datasetUploadResult` 各加 `errorCode` 透傳。
- `ui/src/ui/base.js`：`trainingError` 處理端依 `errorCode` 轉 i18n 文案。
- `src/handlers/trainingOps.ts` / `envOps.ts`（VSIX Host）：postMessage 加 `errorCode: resp.errorCode`。
- `config/python_modules.json` **已含 paramiko 條目** → 文案指向的安裝途徑確實存在（守門 7 驗證）。

### 2.3 F1：燒錄韌體忽略使用者設定的 Python

`reset_firmware` 的 esptool 呼叫寫死 `Command::new("python")`。
**後果**：使用者若在硬體頁把 Python 指向 venv／conda／pyenv（教學環境常見），
`python -m esptool` 會用 PATH 上的另一個 python → 該環境沒裝 esptool → 燒錄失敗，
而錯誤訊息只會說「Failed to start esptool」，使用者完全無從判斷原因。

修法：簽名新增 `python_path: Option<String>`，以 `reset_firmware_python()` 取值（空白回退 `python` 維持舊行為）。
連帶依 AGENTS.md「跨語言 Invoke 簽名同步規範」更新：
`ui/src/bridge/tauri.js`（送 `pythonPath`，取自 localStorage 權威來源）＋ `docs/backend_api_manifest.md` SSOT。

### 2.4 F2：VSIX 韌體燒錄的 shell 注入（本批最嚴重）

`src/handlers/firmwareOps.ts` 以 `terminal.sendText()` 把指令送進**互動式 PowerShell**
（注意：這與 Rust 的 argv 陣列是兩套機制，後者天然安全，前者必須自行跳脫）。原碼：

```ts
let cmd = `& "${pythonPath}" -m esptool ... --port ${serialPort} ...`;
cmd += ` ${seg.addr} "${seg.path}"`;
```

- `--port ${serialPort}` **連引號都沒有** → 埠名含空格即拆成兩個參數。
- `"${seg.path}"` 雙引號包裹：檔名含 `"` → 指令提前截斷，後半段被當獨立命令。
- 檔名含 `$(...)` 或反引號 → **被 PowerShell 展開並執行**（真注入）。
- `seg.addr` 來自 `project_config.json`（外部檔案）且**完全未驗證**。

修法：新增 `psQuote()`（PowerShell 單引號字串跳脫，唯一需跳脫的是單引號本身），
套用於全部 5 個插入點；並在讀 config 時**先驗證 addr 格式**（`0x` 十六進位或 `UF2`，其餘跳過並 warn）。
深 Repair 的 `eTerminal.sendText` 同樣處理。

### 3.3 兩個語意陷阱（搬移必踩）
