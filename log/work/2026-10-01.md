## 3. 技術深挖 (Technical Deep Dive)

### 踩坑記錄 ①：`mock.timers` 而非真等待 —— 測試耗時紅線的實踐

初版 `persistence_snapshot.test.mjs` 的 debounce 測試用 `await new Promise(r => setTimeout(r, 2100))`，
單檔耗時 **6.4 秒**。原因不是 Node 慢，而是 `node --test` 的**測試並發執行**讓 3 個真等待疊在同一時間軸。

違反 AGENTS.md「計時器洩漏紅線」的精神（該條要求測試不得吊住 event loop；真等待雖最終會釋放，
但仍把全量守門從 1.1s 拉高數倍）。

**改法**：改用 `t.mock.timers.enable({ apis: ['setTimeout'] })` ＋ `t.mock.timers.tick(1999)`。
副作用是**更好的斷言**：可以在同一個 tick 內驗「1999ms 不送、2000ms 送一份」這個 debounce 本質，
真等待只能驗「2.1s 後送了恰好一份」。單檔耗時降到 **112ms**。

### 踩坑記錄 ②：測試替身的 `send` 必須回傳 Promise

`setDirty` 的第一版測試報「必須回傳 Promise」失敗。追查後發現：
`persistence.setDirty` **直接回傳** `window.CocoyaBridge.send(...)` 的結果，
而我寫的替身 `send: (cmd) => { events.push(...) }` 回傳 `undefined`。

這不是測試寫錯，而是**精確暴露了計畫 §9.2 的診斷**：
「假 deps 抓不到真 bug」—— 若替身 `send` 回傳 Promise，這條契約就成立；
若回傳 `undefined`，就會在**執行期**讓「await setDirty → close_window」產生競態。
把替身改成 `return Promise.resolve()` 後，測試才如實反映真實 bridge 的行為。

### 踩坑記錄 ④：三段式條件改寫差點造成功能退化

`ui_components.js` 的 `countHeader`：

```js
// 原式：偵測→框數；循線→線段數；其餘（含 table/feature）→樣本數
projectType === 'object_detection' ? BOX_COUNT
  : (projectType === 'line_following' ? LINE_COUNT : SAMPLE_COUNT)
```

我第一版改寫成 `isClassificationType(t) ? SAMPLE_COUNT : (line ? LINE_COUNT : BOX_COUNT)`。
**看似等價，實際讓 `table`／`feature` 顯示「標註框數」** —— 分類統計面板對非影像資料集會顯示錯的單位。

在套用前自我檢查時發現並改用 `needsUnclassifiedCheck(t)`（其語意**恰為** `t === 'object_detection'`），
第一分支完全等價，其餘兩段原封不動。

**教訓**：把 `A === 'x' ? P1 : (B === 'y' ? P2 : P3)` 改寫為 predicate 時，
**必須逐一列舉原表真值再比對**，不可憑「感覺等價」。三段式的**預設分支**（此例是 `P3`）
是最容易放錯的位置 —— 改錯時新 predicate 通常仍能通過大部分測試，因為多數測試只覆蓋兩三種類型。

### 踩坑記錄 ⑤：變異測試要「單獨跑」，不可與其他命令併行

測試新守門時，我把「注入 mutation」與「跑 DM 全量」放在同一個 `run_commands` 批次（並行執行），
導致全量測試在 mutation **尚未還原**時就開始跑，出現 `stats.test.mjs` 莫名失敗。
還原後重跑即全綠。

**教訓**：mutation 測試必須**序列執行**（注入 → 驗證 → 還原 → 再驗），
併到同一批次會讓其他命令讀到中間狀態。

### 12.7 `.gitattributes`：LF/CRLF 根治

**為什麼會反覆發生**：專案原本只有 `core.autocrlf=true`，但它**只在 git 取出檔案時**轉 CRLF。
編輯器／工具直接寫檔不經過 git，工作區就變 LF。

**危害實例**：`typePolicy` 的註解略過正則因行尾多個 `\r` 而失配 → 純註解行被誤判成硬編碼 → 測試誤報紅燈。

**新增 `.gitattributes`**：
```
* text=auto eol=crlf          # 文字檔：repo 存 LF，工作區 CRLF
*.png/*.jpg/*.woff2 ... -text # 二進位不轉換
ui/src/*.min.js -text         # vendored，避免升級套件產生無意義 diff
ui/dist/ target/ -text -diff  # 產物目錄
```

**驗證（不能只看「檔案建立了」）**：
- `git status` 僅 28 條、全為本次變更 → **無關檔案未被連帶標記**（加此檔最常見的災難）
- 屬性正確：`zh-hant.js → text:auto eol:crlf`；`logo.png`／`highlight.min.js → text:unset`
- **實測有效性**：故意把 `en.js` 轉 LF，git 仍只 diff 出 **7 行**（新增的 i18n 鍵），非全檔

### 12.8 事故記錄：Python 同檔讀寫清空三個檔案

處理行尾時寫了
`io.open(p,'wb').write(io.open(p,'rb').read()...)` —— **同一檔案讀寫**，
`'wb'` 會先清空檔案才寫入，導致 `ui_canvas.js`／`annotation.js`／`ui_layout.js` **三檔變 0 bytes**。

`git checkout` 還原（當時為 staged，故從 **index** 而非 HEAD 還回）→ **本次三檔所有修改被回退，全部重做一遍**。

**後續一律採安全寫法**（讀記憶體 → 寫暫存檔 → 原子替換）：
```js
const b = fs.readFileSync(f);
fs.writeFileSync(f + '.tmp', Buffer.from(b.toString('utf8').replace(/\r?\n/g, '\r\n'), 'utf8'));
```

### 13.3 修法：真等待 → mock timers ＋邊界斷言

兩檔的真等待全部改為 `t.mock.timers.enable({ apis: ['setTimeout'] })` ＋ `tick()`。

**關鍵改進不只是變快 —— mock 版能驗真等待做不到的邊界：**

| 測試 | 原真等待 | 改為邊界斷言 |
|---|---|---|
| `loadAnnotationImage` debounce | `sleep(350)` → 只知「350ms 後觸發」 | `tick(299)` 斷言**尚未**觸發 → `tick(1)` 才觸發 |
| `預設 duration 自動清除` | `sleep(60)` → 只知「60ms 後清除」 | `tick(19)` 斷言**尚未**清除 → `tick(1)` 才清除 |
| `duration 0 不自動清除` | `sleep(30)` | `tick(999999)` → 跑再久也不清除 |
| `dispose 取消計時器` | `sleep(70)` | `tick(999999)` → 無殘留回呼 |

**變異測試（兩項皆報紅）**：
1. `annotation.js` debounce 300→100 → `299ms 時 debounce 不應觸發` 報紅
2. `statusMessage.js` 移除 `clearTimeout` → `舊計時器提前隱藏了新訊息` 報紅

> 第 2 項是 AGENTS.md 記載的真實 bug（「顯示前重置全域 `statusMessageTimer`，避免多筆訊息交錯時被舊計時器提前隱藏」）。
> mock 版精準守住，**原真等待版守的是「70ms 後仍顯示」這種弱命題**。
