## 3. 技術深挖 (Technical Deep Dive)

### 踩坑記錄 ①：`mock.timers` 而非真等待 —— 測試耗時紅線的實踐

初版 `persistence_snapshot.test.mjs` 的 debounce 測試用 `await new Promise(r => setTimeout(r, 2100))`，
單檔耗時 **6.4 秒**。原因不是 Node 慢，而是 `node --test` 的**測試並發執行**讓 3 個真等待疊在同一時間軸。

違反 AGENTS.md「計時器洩漏紅線」的精神（該條要求測試不得吊住 event loop；真等待雖最終會釋放，
但仍把全量守門從 1.1s 拉高數倍）。

**改法**：改用 `t.mock.timers.enable({ apis: ['setTimeout'] })` ＋ `t.mock.timers.tick(1999)`。
副作用是**更好的斷言**：可以在同一個 tick 內驗「1999ms 不送、2000ms 送一份」這個 debounce 本質，
真等待只能驗「2.1s 後送了恰好一份」。單檔耗時降到 **112ms**。

### 踩坑記錄 ②：測試替身的 `send` 必須回傳 Promise

`setDirty` 的第一版測試報「必須回傳 Promise」失敗。追查後發現：
`persistence.setDirty` **直接回傳** `window.CocoyaBridge.send(...)` 的結果，
而我寫的替身 `send: (cmd) => { events.push(...) }` 回傳 `undefined`。

這不是測試寫錯，而是**精確暴露了計畫 §9.2 的診斷**：
「假 deps 抓不到真 bug」—— 若替身 `send` 回傳 Promise，這條契約就成立；
若回傳 `undefined`，就會在**執行期**讓「await setDirty → close_window」產生競態。
把替身改成 `return Promise.resolve()` 後，測試才如實反映真實 bridge 的行為。

### 踩坑記錄 ④：三段式條件改寫差點造成功能退化

`ui_components.js` 的 `countHeader`：

```js
// 原式：偵測→框數；循線→線段數；其餘（含 table/feature）→樣本數
projectType === 'object_detection' ? BOX_COUNT
  : (projectType === 'line_following' ? LINE_COUNT : SAMPLE_COUNT)
```

我第一版改寫成 `isClassificationType(t) ? SAMPLE_COUNT : (line ? LINE_COUNT : BOX_COUNT)`。
**看似等價，實際讓 `table`／`feature` 顯示「標註框數」** —— 分類統計面板對非影像資料集會顯示錯的單位。

在套用前自我檢查時發現並改用 `needsUnclassifiedCheck(t)`（其語意**恰為** `t === 'object_detection'`），
第一分支完全等價，其餘兩段原封不動。

**教訓**：把 `A === 'x' ? P1 : (B === 'y' ? P2 : P3)` 改寫為 predicate 時，
**必須逐一列舉原表真值再比對**，不可憑「感覺等價」。三段式的**預設分支**（此例是 `P3`）
是最容易放錯的位置 —— 改錯時新 predicate 通常仍能通過大部分測試，因為多數測試只覆蓋兩三種類型。

### 踩坑記錄 ⑤：變異測試要「單獨跑」，不可與其他命令併行

測試新守門時，我把「注入 mutation」與「跑 DM 全量」放在同一個 `run_commands` 批次（並行執行），
導致全量測試在 mutation **尚未還原**時就開始跑，出現 `stats.test.mjs` 莫名失敗。
還原後重跑即全綠。

**教訓**：mutation 測試必須**序列執行**（注入 → 驗證 → 還原 → 再驗），
併到同一批次會讓其他命令讀到中間狀態。
