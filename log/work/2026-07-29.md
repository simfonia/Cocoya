## 技術深挖 (Technical Deep Dive)

### serde rename_all = "camelCase"
Rust 的 serde 預設序列化欄位名稱為 snake_case，與 JavaScript 的 camelCase 不匹配。解決方式是在 struct 上加 `#[serde(rename_all = "camelCase")]`，這會自動將 `blob_url` 序列化為 `blobUrl`。

### Tauri asset protocol 與 convertFileSrc
Tauri 2.0 的 asset protocol 允許 webview 載入檔案系統的檔案。`convertFileSrc` 會根據平台自動產生正確的 URL 格式：
- Windows: `http://asset.localhost/<url-encoded-path>`
- macOS/Linux: `asset://localhost/<path>`

手動構建 URL 容易出錯，建議使用官方 API。

### Tauri DialogExt trait
`Window` 實作 `DialogExt` trait，提供 `dialog()` 方法開啟原生對話框。`State<AppState>` 不實作此 trait，必須使用 `window` 參數。

### 4. Value 積木程式定位修復 (CodeBridge 技術移植)

#### 探索 Phase
- 探索 CodeBridge (`C:/Workspace/CodeBridge/`) 的程式定位技術
- CodeBridge 在 `ui/src/main.js` 實作 `findLocatableBlock(block)`：若積木有 `outputConnection`，遞迴往上找到 statement 父積木
- CodeBridge 在 `ui/src/lib/blockly/generators/_core.js` 的 `scrub_` 中，僅在換行處注入 `// __BLOCKLY_ID:xxx__` 標記 (單行 value 積木不標記)
- CodeBridge 的 `syncSelection` 使用 `findLocatableBlock` 找到可定位父積木後，再以其 ID 查找範圍

#### 根本原因分析
- Cocoya 在 `ui/src/utils/generators.js` 的 `scrub_` 中，對 value 積木使用 invisble 標記 `\u0001ID:xxx\u0002`
- 但 `ui/src/app/workspace.js` 的 `triggerCodeUpdateSync` 中，`code.replace(/\u0001ID:.*?\u0002/g, '')` 清除了這些標記
- 導致 `blockToRangeMap` 中沒有 value 積木的 ID
- 同時 `ui/src/ui/renderer.js` 的 `syncSelection` 直接以 `blockId` 查找，缺少遞迴查找機制

#### 修復
- **`ui/src/ui/renderer.js`**：
  - 新增 `findLocatableBlock(block)` 方法 (參考 CodeBridge 實作)
  - 修改 `syncSelection`：使用 `findLocatableBlock` 找到可定位父積木後，再以其 ID 查找範圍
- **`docs/system_spec.html`**：在「積木定位技術」章節補充 subsection D

#### 技術深挖
- Value/expression 積木 (有 `outputConnection`) 的程式碼是內嵌在父 statement 積木之中
- 它們通常沒有自己的範圍標記 (statement 標記 `# S_ID`/`# E_ID` 僅在 statement 積木上)
- CodeBridge 的解法：不標記 value 積木，改為遞迴查找父 statement 積木
- Cocoya 的解法：標記 value 積木但被清除，改為遞迴查找 (與 CodeBridge 一致)
- `findLocatableBlock` 的遞迴終止條件：找到沒有 `outputConnection` 的積木 (statement 積木)
- 邊界情況：naked value (無父積木) → `findLocatableBlock` 返回原積木本身

### 7. 修復 Minimap 工作區註解同步問題 (v2 - 完整重新載入法)

#### 問題描述
- 工作區註解功能啟用後，Minimap 不會即時更新工作區註解
- 使用者詳細回報：
  1. 開啟舊檔，註解正確顯示，minimap 也正確
  2. 移動積木，minimap 正確更新
  3. 移動或新增註解，minimap 沒有更新

#### 根本原因分析
- `workspace.js` 的 `initMinimap()` 中，覆寫了 `minimap.mirror()` 函數
- **第一層問題**：原函數過濾掉了不包含 `blockId` 的事件
  - 工作區註解事件使用 `commentId` 而非 `blockId`
- **第二層問題**：minimap 內部的 `p Set` 不包含註解事件
  - `p = new Set([BLOCK_CHANGE, BLOCK_CREATE, BLOCK_DELETE, BLOCK_DRAG, BLOCK_MOVE])`
  - 註解事件不會觸發 minimap 內部的 update() 函數

#### 解決方案 (v2 - 完整重新載入法)
- **`ui/src/app/workspace.js`**：
  - 在 `minimap.mirror()` 中加入註解事件識別邏輯
  - 對於註解事件，使用完整重新載入：`workspaceToDom` → `clear` → `domToWorkspace`
  - 不使用 `originalMirror(event)` 增量更新
  - 這樣可以確保註解事件正確同步

#### 技術細節
- Blockly 工作區註解事件類型：
  - `COMMENT_CREATE`：建立註解
  - `COMMENT_DELETE`：刪除註解
  - `COMMENT_CHANGE`：修改註解內容
  - `COMMENT_MOVE`：移動註解
  - `COMMENT_RESIZE`：調整註解大小
- 這些事件使用 `commentId` 而非 `blockId`
- Minimap 的 `mirror()` 函數內部的 `p Set` 只包含積木事件，不包含註解事件
- 完整重新載入可以確保 XML 序列化/反序列化的一致性

- [x] 新增/移動註解有即時更新 minimap
