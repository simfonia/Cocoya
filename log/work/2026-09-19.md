### 額外發現並修正的既有 bug（micro:bit 腳位全部 miss）
驗證新 maker-pi 資料時，順手寫的「所有板 `pins[].ref` 必可解析」檢查**當場抓到 micro:bit 全數失敗**：

### 技術深挖 (Technical Deep Dive)

#### 1. 為什麼 pin map 這種「純資料」也會壞？——兩個獨立的資料／管線契約
本日與昨日兩個 bug 說明同一症狀有兩條不同的失效路徑：
1. **管線污染**（09-18）：`valueToCode()` 回傳值在產生期間帶著 `\u0001ID:...\u0002`，資料本身正確但字串被污。
2. **資料鍵不一致**（09-19）：`pins[].ref` 的正規化結果與 `gpioMap` 的鍵不同（`pin0` vs `P0`）。
兩者都在同一個入口 `resolveGpio()` 收斂（先 `normalizePinRef` 再查表），所以修正點集中、風險低。
**制度化解法**：把「所有板的所有 ref 必須可解析」寫成測試（不變式），資料錯誤在 CI/本機測試即現形，不必等實機。

#### 2. 為什麼標籤（label）可以自由改，而 ref 不行
`ref` 是舊專案 XML（`mcu_pin_shadow` 的 `field` 值）與 `gpioMap` 的查表鍵；`label` 只是下拉顯示文字。
因此本次把「教學價值」（`GP8 (M1A)`、`GP12 (Servo)`）加在 `label`，`ref` 完全不動 → 所有既有專案行為不變、零遷移成本。
未來若要做 i18n 的下拉文字，應改在 `pinOptions()` 以 boardId+ref 查 i18n key，而不是把中文寫進資料層（本輪刻意維持資料層語言的語言中立性：使用 M1A/Servo/Grove 等業界通用詞）。

#### 3. `tags` 的定位（預留欄位）
`tags` 目前無人消費（todo 仍列「依 tags 過濾腳位下拉」為待辦）。本次依 datasheet 把 `i2c/uart/spi` 也標上，
未來實作過濾時可直接 `tags.includes('adc')` 等；若屆時採白名單語意，需注意「加 tag 只會增加選項」的相容性方向（寧可寬鬆、不可缺漏）。

#### 4. 為何 datasheet 的 GP26 重複出現要照登
Grove 5（GP6/GP26）與 Grove 6（GP26/GP27）在原文共用 GP26。硬體上 GP26 是 ADC0 且被拉出到多個埠的 A0 位置是常見設計；
但 Cocoya 的 `pins` 是下拉清單，**同一 ref 不可重複**，故 GP26 僅登錄一次，label 記為 `GP26 (Grove 5/6, ADC0)` 保留雙埠資訊。

#### 5. 抓取 Google Docs 的正確姿勢
`/edit?tab=t.0` 回傳的是 JS 殼（標題可見、內容不可見）；`/export?format=txt` 可直接取得純文字（本文件約 6.3KB），
是本機除錯／規格萃取的可重用技巧（已在 `HardwarePinMap.html` 註明資料來源與版本）。

### 技術深挖 (Technical Deep Dive)
- **假幀驅動的協定行為測試**：把積木產生器注入的 Python 輔助類抓出（`generator.definitions_['class_huskylens']`），串接 Python harness（stub `machine` 模組、stub `time.sleep_ms`、可排程回傳值的假 I2C/UART），以官方欄位偏移人工組幀（V2 `55 AA CMD ALGO LEN DATA SUM`；V1 `55 AA 55 AA ADDR LEN CMD DATA SUM`），`spawnSync` 執行後取 JSON 驗證。此法鎖住「欄位偏移」與「指令碼」兩類最易寫錯的契約，且不需實機。
- **類別內 print 會污染 stdout**：V1 守門分支會印提示訊息（設計如此），harness 以 `__JSON__` 哨兵行包住結果、JS 只解析哨兵行（首次直接 `JSON.parse(stdout)` 失敗）。
- **V1 checksum 範圍易錯**：V1 的 SUM 只涵蓋 ADDR..DATA（不含 `55 AA 55 AA` 標頭），V2 才是「除 checksum 外全」。測試 helper 分為 `sumOk`（V2）與 `sumOkV1`（V1）；此點亦為實機握手失敗的第一檢查項。
- **V2 指令碼逐條確認**：由 `ProtocolV2.cpp` 確認 LEARN=0x22、FORGET=0x23、SAVE_KNOWLEDGES=0x24、LOAD_KNOWLEDGES=0x25、SET_NAME_BY_ID=0x0B（先前僅 SET_ALGORITHM=0x0A 有把握）。
- **name 欄偏移**：V2 RETURN_BLOCKS 的 data[10]=nameLen、data[11..11+n]=name，與 `Result.h` / 協定文件一致；content length 緊接其後（本模組未使用）。

### 討論結論（使用者提問三項）
1. **V1 控制器是否正確**：使用者於 V1 時期以「起點 x 比例（回中位）+ deltaX/deltaY（預測）」調差速，判定為**教科書級正確做法**（＝橫向誤差 P + 航向誤差 D 的 PD 控制）。注意事項：V1 中心為 160（座標系 320x240）、deltaY→0 奇異點需 `max(deltaY, ε)`、需死區與限幅。
2. **DM 標註只要目標點嗎**：**不建議**。事實核對：DM 線標註為兩點 `{class_id, line:[x1,y1,x2,y2]}`（`ui_canvas.js:16-17`）→ 匯出 `lines/<name>.txt` 一行 `x1 y1 x2 y2`（`common/line_dataset.py:8,68`）→ `line_follower_train.py` 用 `Dense(4, sigmoid)` 回歸、**輸出即為兩端點**（檔頭註解明示「語意為線段端點，非 bbox」）。改單點會失去航向（D 項）資訊。
3. **釐清「兩個循線世界」**：世界 A＝HuskyLens 內建循跡（不訓練，受 V1/V2 起點語意限制）；世界 B＝Cocoya 自訓循線模型（DM 兩點標註 → Dense(4) → 部署，天然是 V1 語意）。V2 固定起點的限制只影響世界 A。
