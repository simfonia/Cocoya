## #task[依開發板更新腳位資訊] 腳位無法解析根因（scrub_ 不可見 ID 標記污染）修復

### 症狀（使用者回報）
放置 `mcu_board_init`（Maker Pi RP2040 cap 積木）後，腳位相關積木仍無法解析：

```python
# Board: Maker Pi RP2040 (maker-pi)      ← 板名正確
# [Cocoya] 無法解析腳位: board.GP0 （請確認已選擇開發板，或改用腳位下拉選單）  # S_ID:...
pass  # E_ID:...
```

板子資訊正確、序列埠正常，但所有走 `mcu_pin_shadow`（腳位下拉）的積木都產生錯誤註解。

### 根因（100% 證實，非猜測）
`ui/src/utils/generators.js:46` 的高亮同步攔截器會為**所有具 output 連線的積木**前置不可見標記：

```js
Blockly.Python.scrub_ = function(block, code, opt_thisOnly) {
    if (block.outputConnection) return `${s}ID:${block.id}${e}${code}`;   // s=U+0001, e=U+0002
```

`mcu_pin_shadow` 正是 output 積木（`hardware_blocks.js:151` `"output": "String"`），其產生器回傳 `JSON.stringify(pin)`（`hardware_generators.js:6`），於是：

| 階段 | 內容 |
|---|---|
| 產生器回傳 | `"board.GP0"` |
| 經 `scrub_` 包裹 | `U+0001ID:c8xk...U+0002"board.GP0"` |
| `valueToCode('PIN')` 取出 | 同上（Blockly 核心 `blockToCode` 對 output 積木回傳 `scrub_(block, code)`；`valueToCode` 直接取用） |
| `CocoyaBoard.resolveGpio` | 只 `.replace(/['"]/g,'')` + `.replace(/^board\./,'')` → 字串以 U+0001 開頭 → 前綴去除失敗 → 標記殘留 |
| gpioMap 查表 + 全板兜底掃描 | key 已被污染 → 皆 miss → `null` |
| 結果 | `cocoyaPinErrorComment()` → `# [Cocoya] 無法解析腳位: ...` |

**為何戴口罩（極難察覺）**：
1. 標記是 U+0001/U+0002 控制字元，肉眼與貼上文字都看不出來。
2. `ui/src/app/workspace.js:334` 於預覽前 `code.replace(/\u0001ID:.*?\u0002/g, '')` → 最終生成碼乾淨。
3. 錯誤訊息自身也只去引號（`hardware_generators.js:34`），髒標記被一起帶進註解但不可見。

**為何只有腳位失敗**：`boardName`／`mcu_car` 的 PIN 皆走 `getFieldValue()`（field 值，不經 `valueToCode`，無標記）；只有 `hardware` 模組的腳位走 `mcu_pin_shadow`（value 輸入）→ 唯一受污染路徑。

### 技術深挖 (Technical Deep Dive)

#### 1. 為什麼這個 bug 從 2026-09-06 實作起就存在，卻「實機驗證 PASS」？
`scrub_` 的 value 標記是**高亮同步系統**（code ↔ 積木雙向定位）的既有設計，09-06 的驗證極可能是：
(a) 用 `mcu_car` 的 field 型腳位積木測試（該路徑無標記，確實正常），或
(b) 在 console 直接呼叫 `CocoyaBoard.resolveGpio('maker-pi','board.GP0')` —— 手寫字串沒有標記，必然 PASS。
**教訓**：驗證「產生器」必須走真正的 `workspaceToCode` 管線（或等價的 `valueToCode` 注入），不能只驗證被呼叫的純函式。

#### 2. 為何不能「把標記拿掉」了事（方案取捨）
- 標記供 `ui/src/ui/renderer.js` 的 `extractIds` / `lineIndexToBlockId` 做行↔積木對應（點程式碼跳到積木）。移除 value 標記可能影響 value 積木的精準定位。
- 因此本輪採「**在語意邊界剝除**」：`resolveGpio` 是腳位語意的唯一入口，在此剝除最安全、零改動高亮機制。
- 治本方案（列 backlog）：讓 value 標記不流入產生器邏輯（例如 `scrub_` 對 value 積木改以非 code 汙染的方式記錄），需先確認高亮同步是否依賴 value 標記。

#### 3. 為什麼錯誤訊息裡的髒標記「看得見」卻沒人發現
`cocoyaPinErrorComment` 把**未去污**的 `pinCode` 串進註解，最終 `workspace.js` 會把 `U+0001ID:...U+0002` 清掉 → 使用者看到的是乾淨的 `board.GP0`；但若該字串被寫入 log/錯誤回報（未經清理路徑），就會靜默帶入不可見字元。本次一併在訊息產生端去除。

#### 4. 可重用的診斷手法（本次新工具）
以 `new Function(fs.readFileSync(file))` + `globalThis.window = globalThis` + `Blockly` stub，即可在 **Node 無 GUI** 環境載入瀏覽器模組並對產生器做端到端測試：

```js
globalThis.window = globalThis;
globalThis.Blockly = { Blocks: {}, Msg: {}, Python: { forBlock: {} } };
const load = (rel) => new Function(fs.readFileSync(rel, 'utf8'))();
load('ui/src/modules/hardware/board_defs.js');   // 依序載入
```
此模式已固化為 `pin_resolve.test.mjs`，日後任何「產生器語意」bug 都可照抄。
