# 2026-09-09 工作日誌

## 任務：#task[bug修正] 上傳 Maker Pi RP2040 成功後終端只顯示「OK」而非 complete_banner

### 症狀
上傳程式到 Maker Pi RP2040 成功後，終端機訊息停在孤伶伶的一行 `OK`，
沒有出現預期的 `complete_banner`（`[上傳成功] 程式已存入 Flash 並開始執行！`）。

```
----------------------------------------
--- 序列埠監控: COM7 ---
----------------------------------------

OK
```

### 根因（兩層）
1. **「OK」的來源**：`micropython.py` 的 `deploy()` 送 `ser.write(b"\x04")`（Ctrl-D）讓 MCU 執行
   暫存內容。MicroPython/CircuitPython 的 Raw REPL 協定下，程式**成功執行結束**時韌體會主動回傳
   一字面的 `OK`（失敗則回 traceback）→ 畫面最後一行的 `OK` 是**韌體層級的執行成功標記**，
   既不是 Cocoya 印的，一般也不是使用者程式的 print。
2. **complete_banner 為何未印出**：`resources/deploy/base.py` 的 `monitor()` 中，逾時補印檢查
   `time.time() - banner_timer > 2.0` 被放在 `if ser.in_waiting > 0:` **區塊內部**。Raw REPL
   執行完只回 `OK`（不回 normal REPL 的 `>>>`，也不含 `soft reboot`），且 MCU 隨後停在 raw
   prompt、**不再主動送資料** → `ser.in_waiting > 0` 永遠為 false → 該逾時分支永遠不會被執行 →
   `banner_pending` 永久為 True → complete_banner 永不印出。

### 修正（resources/deploy/base.py monitor 迴圈）
- 資料處理區內移除逾時檢查，僅保留 `soft reboot` / `>>>` 結束訊號即時觸發（維護 09-07 設計：
  pending 期間仍寫出資料，避免吃掉程式開頭 print）。
- 新增「banner 兜底」：在 `while` 迴圈層級、資料區之外，若 `banner_pending` 且距開始已逾 2 秒
  （例如 Raw REPL 停在 raw prompt 無後續資料），強制補印 `welcome_msg`（= complete_banner）。
  如此無論 MCU 停在哪種 prompt、有沒有後續序列資料，complete_banner 都保證會在 2 秒內出現。

### 異動檔案
| 檔案 | 內容 |
|------|------|
| `resources/deploy/base.py` | `monitor()` banner 兜底：逾時檢查移出資料區、放到 while 層級 |

## 任務（續）：上傳後序列埠輸出空行不穩定復現（完成，含踩坑記錄）

### 症狀演變（多輪迭代，先記錄以免遺忘）
1. banner 修好後發現每道 print 多一個空行；VSIX 無空行、Tauri 有 → 定位為**渲染層差異**。
2. 進一步修正 banner 提前（`micropython.py` 在送 Ctrl-D 前先印 complete_banner，監看改 `existing_ser` 接管且不再傳 welcome_msg）。
3. 空行出現位置每次不同（0/1、5/6、1/2 輪流跳）→ 排除 1.5s 熱插拔輪詢（`lib.rs` 輪詢僅列舉埠、不開埠偷讀）。
4. 嘗試 Rust `emit_line_buffered` 整行緩衝一度成功，但之後又復現；且出現 `OKHello : 0` 黏行。

### 最終根因（raw dump 實測抓到，非猜測）
`base.py` monitor 加 `raw_dump.log`（每批原始 bytes repr）診斷後，實測序列埠資料到達模式：

```
b'OK'  b'Hello Cocoya : 0'  b'\r\n'  b'Hello Cocoya : 1'  b'\r\n' ...  b'\x04'  b'\x04>'
```

**關鍵**：RP2040 送 `Hello:0` 與其換行 `b'\r\n'` 是**兩個獨立批次**到達。空行製造鏈：
1. base.py 收到純 `b'\r\n'` 批 → 剝 `\r` 後剩 `\n`，被當「有資料」輸出一個 `\n`；
2. 之前 Rust `emit_line_buffered` 又把 base 產的 `OK\n\n` 拆成 `OK\n` + 純 `\n` 兩筆；
3. 前端 `white-space: pre-wrap` 把那個多餘 `\n` 渲染成空行。批次切分依時序漂移 → 空行位置不穩定。

### 最終修復（三層明確分工）
| 層 | 檔案 | 修正 |
|---|---|---|
| 源頭 | `resources/deploy/base.py` | monitor 輸出前**過濾「純換行批」**（`strip()` 為空則不輸出，換行由每行補 `\n` 涵蓋）；壓平段內 `\n{2,}`；`OK` 後補一個空行（壓平之後再做，避免被吃掉）；剝 `\r`、`→\n`；跨批次前導 `\n` 收斂 |
| 傳輸 | `src-tauri/src/commands/mcu.rs` | **移除 emit_line_buffered 整行切分，回復 chunk 直通**——不拆散 base 已產好的乾淨輸出，空行控制單一源頭在 base.py |
| 渲染 | `ui/src/bridge/tauri.js` | python-log listener 剝 `\r`（xterm 會吸收 \r，DOM pre-wrap 不會，故需收斂），不做其他猜測 |

另外**同步副本**：`src-tauri/target/debug/resources/deploy/base.py` 需與 repo 根同步（dev 模式實際執行的是副本），並清 `.pyc`。

### 踩坑記錄（蒸餾）
1. **Raw REPL 輸出三特性**：(a) 程式成功執行完回字面 `OK`（失敗回 traceback）；(b) 輸出段落以 `\x04` 分隔、結尾 `\x04>`；(c) 換行常為 `\r\n\r\n` 且**換行會與內文分批到達**（`Hello:0` 一批、`\r\n` 另一批）。
2. **序列埠分批到達是時序決定**：任何「單批內壓平」都會被跨批次的 `\n\n` 擊穿，且位置每次不同——必須過濾「純換行批」＋跨批收斂，或讓單一層（base.py）做全部文字整理。
3. **Tauri DOM 虛擬終端 vs VSCode xterm**：xterm 吸收 `\r`/重複換行；`pre-wrap` 每個 `\n` 都強制換行 → 同一份輸出兩平台渲染不同，終端機文字需在進入 pre-wrap 前收斂。
4. **Rust 整行緩衝（split 換行 emit）是雙面刃**：對 raw 直通流有效，但會拆散上游已排版好的文字（`OK\n\n` 被拆成兩筆反而製造空行/黏行）。上傳路徑應「上游排版、傳輸直通」。
5. **`target/debug/resources` 副本陷阱**：改 repo 根的 `resources/deploy/*.py` 後，dev 執行的是 target/debug 下的副本，必須同步（或重 build），否則修改看起來「沒生效」。
6. **banner 逾時檢查不可關在 `ser.in_waiting > 0` 區塊內**：MCU 停在無輸出狀態時該分支永不執行；逾時兜底必須放在迴圈層級。
