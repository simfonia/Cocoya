### 技術深挖 (Technical Deep Dive) — 根因
**控制通道與廣播通道 multiplex 同一條 socket，而 module 層 lease API 用「盲讀一行」當回應。**

- 診斷腳本：`temp/scripts/debug_hub_lease.py`（攔截 `_read_json_line` 記錄實際訊息，5/30 重現）。trace 證據：
  - 失敗模式 1：第二次 `acquire_upload_lease` 讀到 `{'type': 'state', 'connected': False}`（廣播），不是 `{'ok': False, 'error': 'SERIAL_PORT_BUSY_UPLOAD'}`（回應）。
  - 失敗模式 2：lease socket 上殘留 acquire 時 `_broadcast({'type':'state','connected':False,'reason':'upload'})`（serial_hub.py:592），`release_upload_lease` 的 `_read_json_line` 讀到這條 stale 廣播就立即回傳 → 沒等到真正的 release 回應 → 立刻 assert 時 server 還沒處理完。
- 機制：admin client 在 hello 後加入 `self.clients`（serial_hub.py:521），`_broadcast` 會送狀態/資料訊息給它；`acquire_upload_lease`/`release_upload_lease`（serial_hub.py:689/705）卻以 `_send_json` + 單次 `_read_json_line` 對話，中間插入的廣播會被誤當回應。
- 對照：`SerialProxy._request`（serial_hub.py:265）用 `requestId` + 背景 reader thread 拆包，**不受此 race 影響**；只有 module 層兩個 lease 函式有病。
- 影響面（不只測試）：Rust `deploy.rs --lease` helper 與 `base.py` 都走這兩個函式 — 真機上可能對上傳衝突出現錯誤碼退化（`SERIAL_PORT_BUSY` 而非 `..._UPLOAD`），及 release 過早回傳的視窗期。
