## #task[cocoya TDD 架構檢查] TDD 精簡化施工（分層守門）

### 起因
使用者反映「每次修改都要跑 TDD 花很多時間」，並詢問測試執行是否會消耗 AI token。
先量測現況再動手，結論是**問題不在測試品質（194/194 全綠），而在守門機制太粗**。

### 量測基準（實測，非估算）
| 項目 | 量測值 |
|---|---|
| 全量 `node --test "src/**/*.test.mjs"` | **5722ms**、輸出 12,439 字元（≈3,500 token） |
| `--test-reporter=dot` | 205 字元（≈60 token） |
| 34 個測試檔逐檔耗時 | `statusMessage.test.mjs` **5167ms**；其餘 28 檔 148~190ms（Node 啟動開銷）；前 5 名其餘為 annotation 534 / line_inference 416 / huskylens 273 / io/bridge 240 / core_contract 199 |
| `.github/workflows`、`ui/test/` | 不存在 |
| Rust `#[test]` | 3 個（mcu.rs 2、dataset.rs 1） |

### 根因：90% 時間是空轉
`ui/src/modules/dataset_manager/ui/statusMessage.js` 的預設 `duration = 5000`，
而 `statusMessage.test.mjs` 前兩個案例以預設值呼叫 `showStatusMessage()` 後**未 `dispose()`**，
未清除的 `setTimeout` 吊住 Node event loop，強制等待整整 5 秒才結束。

實測佐證（直接 import 產品碼量測 event loop 存活時間）：
```
node -e 'import statusMessage.js → showStatusMessage("hello")' → held alive ms=5004
```
→ 該單檔 5167ms，佔全量 5722ms 的 **90%**；DM 子樹 149 測試的 6000ms 中有 5000ms 是空等。

### 修改內容

**1. 修掉計時器洩漏（只動測試，不動產品碼）**
`ui/src/modules/dataset_manager/ui/statusMessage.test.mjs`
- 「顯示訊息」與「空訊息」兩案例改為 `showStatusMessage('hello', { duration: 0 })`
- 補註解說明：只驗顯示瞬間時不需要計時器，否則整個測試檔多等 5 秒
- 效果：單檔 5167ms → **542ms**（`pass 7 / fail 0` 不變）

**2. 三層測試腳本（避免每次都全跑）**
`package.json`（根）：
```json
"test":      "npm run test:unit && npm run test:ui",
"test:unit": "npm run compile && npm run lint",
"test:ui":   "npm --prefix ui run test:unit",
"test:dm":   "npm --prefix ui run test:dm",
"test:core": "npm --prefix ui run test:core",
"test:fast": "node scripts/test-related.cjs",
"test:rust": "cargo test --manifest-path src-tauri/Cargo.toml"
```
`ui/package.json`：`test:unit`（全量）／`test:dm`（DM 149 例）／`test:core`（core 契約）。
- **不用 `cd ui && ...`**：改用 `npm --prefix ui run`，消除 cmd.exe 與 pwsh 的 `&&`／`;` 差異。
- **不用目錄模式**（`node --test src`）：會誤把 `index.js` 當入口（AGENTS.md 既定紅線）。

**3. `scripts/test-related.cjs`（L0 自動挑測試，新增）**
- 來源：`git diff --name-only HEAD` ＋ `git ls-files --others`，或命令列指定檔案
- 挑選順序：**同名測試**（改 `statusMessage.js` → `statusMessage.test.mjs`）→ 同目錄全部 → 模組 glob
- 契約敏感檔（`*_blocks.js`／`*_generators.js`／`toolbox.xml`／任何 `i18n/*.js`／`src/zh-hant.js`／`src/en.js`／`core_manifest.json`／`theme_manager/themes/*.js`）一律納入 `core_contract.test.mjs`
- 非 `ui/` 檔案（Rust／VSIX TS／Python）不跑 Node 測試，改提示對應命令（`cargo check`／`tsc --noEmit`／`py_compile`）
- 支援 `--dry` 只列不跑

### 技術深挖 (Technical Deep Dive)

**Q：為什麼不用 `--test-reporter=dot`，而是自己過濾輸出？**
`dot` reporter 輸出只有 205 字元，但**沒有 `tests/pass/fail` 摘要行**（實測輸出僅 10 行點點），
失去「一眼判斷紅綠」的能力，且失敗時無從得知哪個 case 紅。
因此 `test-related.cjs` 改採「**用預設 spec reporter 執行 → 於腳本內過濾成摘要 + 失敗明細**」。
過濾發生在子行程輸出落地**之前**，所以對話上下文只會看到約 8 行，
但保留了完整判讀能力。量測：12,439 字元 → 約 400 字元（省 95%）。

**Q：為什麼逐檔耗時都在 150ms？**
那是 Node 每啟動一個測試檔的固定成本，不是測試邏輯本身。
`node --test` 對多檔預設平行執行，故全量 34 檔只需約 1.1 秒；
但**逐檔序列執行時**這 150ms 會累加成 5.1 秒——這也是「不要逐檔跑量測」的技術理由。

**Q：`test:fast` 會不會漏測？**
會，但這正是分層的目的。契約變更（積木／產生器／i18n／主題）一定會拉進 `core_contract.test.mjs`；
純 VSIX TS／Rust／Python 異動則提示改跑 `tsc`／`cargo`／`py_compile`。
**階段收尾仍必須 `npm run test:ui`（全量）或 `npm test`（compile+lint+全量）。**

## 修掉的三類問題

### 1. `no-dupe-keys`（3 處）—— **全是真 bug：i18n 鍵被靜默覆蓋**

### 2. `no-case-declarations`（1 處）
`bridge/tauri.js` 的 `case 'getModuleToolbox'` 直接在 case 下宣告 `const toolboxPath`。
switch 的所有 case 共用同一個區塊作用域，與其他 case 的同名 `const` 會互相覆蓋／衝突。
→ 包成獨立 block（該檔 `case 'datasetCaptureImage'` 已有同樣寫法先例）。

### 3. `no-unused-vars`（14 處）
| 位置 | 處理 | 理由 |

→ 補上說明註解。ESLint 的 `no-empty-function` 會忽略含註解的函式體，同時也讓

# Stable Mode 整條移除（CircuitPython 遺留，2026-09-30）

## 為什麼是 CircuitPython 遺留
使用者確認：該功能是**先前使用 CircuitPython 時的遺留，本專案已不再支援 CircuitPython**。
Cocoya 目前只支援 MicroPython／Pybricks／官方 SPIKE（見 `deploy_mcu.py --board-type` choices）。
CircuitPython 在開機時不會自動執行 `boot.py`（那是 MicroPython 的行為），
故「寫入 `boot.py` 使 MCU 開機自動執行」這個設計對 CircuitPython 本來就不適用。

## 關鍵發現：整條鏈從未真正運作過
| 層面 | 狀態 |
|---|---|
| `index.html` | **從未有** `btn-setup-stable-mcu` 元素 |
| `base.js` 的綁定 | `if (setupStableBtn)` → 永遠 false（no-op） |
| `base.py:274` | `print("\n[Notice] Stable mode not required for this firmware.")` |
| `micropython.py:153` | `print("\n[Notice] MicroPython does not need 'Stable Mode'...")` |
| `pybricks.py:131` | `print("\n[Notice] Pybricks firmware is already optimized...")` |

三個韌體實作**都只印一行訊息**，不寫入 `boot.py`、不鎖定磁碟。
而 `MSG_SETUP_STABLE_CONFIRM` 的文案卻宣稱「Windows 會變唯讀、Cocoya 改以序列埠上傳」
——**文案與實際行為完全不符**。這是不移除就會誤導使用者的關鍵理由。

### 技術深挖 (Technical Deep Dive)
**1. 刪除未用 import 的副作用風險（先查證再動）**
`index.js` 的 `import { UIComponents } / { UICanvas }` 看似死碼，但若該模組靠**頂層副作用**自我註冊，刪 import 就會靜默壞掉。動手前先確認：
- `ui_components.js` 僅 `export const UIComponents = {...}`，**無 `window.*` 指派、無 `addEventListener`、無頂層 `document` 存取** → 純物件，刪除安全。
- `ui_layout.js` 本身就 import 並使用兩者（`UICanvas.state` 於 `removeAnnotation`），模組仍會被載入。
→ 結論：可安全刪除未用 import。**日後刪任何 import 前都應先做這一步查證。**
**2. `ui/panels.js` 的 `doc()` 與 `getDocument` 是整條死鏈**
`function doc() { return getDocument(); }` 從未被呼叫（容器一律走 `getModal()`）。若只刪 `doc()` 不刪參數，`getDocument` 立即變成新的未用變數 → **必須連帶移除 destructure 參數、JSDoc `@param` 說明、與文件頭的依賴清單**，共 4 處同步。
**3. Blockly generator 簽名的兩種呼叫路徑（決定能否刪 `generator` 參數）**
- statement 型：`statementToCode` → `generator(block)`
- value 型：`valueToCode` → `(block, name, order)`
兩者都**不傳 `generator` 給 generator 函式本身**（`generator` 是產生器物件，由 Blockly 內部持有）。故函式宣告 `generator` 參數從來都是多餘的。實作時還踩到一個啟發式陷阱：先寫腳本用「往下 40 行找 `block.`」判斷 `block` 是否被用，結果視窗跨到**下一個函式**而誤判，5 處 huskylens 保留殘留參數。→ **語意掃描必須限縮在同一函式體內**，最終以 eslint 掃描結果為準，不靠腳本猜。
**4. `no-useless-escape` 在 mcu_car 的三層字串陷阱 — 查證後確認「非 bug」**
`mcu_car_generators.js` 模板字串（`MUSIC_ENGINE_INJECT`）內有 Python raw string：
`pattern = r"([A-GR][#S]?)([0-8])?([WHQEST\._T\+]+)"`
初判為 AGENTS.md「三層字串意識」警告的**真轉義 bug**（模板字串會吃掉 `\.` 的反斜線）。**實測後推翻**：
- node 驗證：`\.` → `.`、`\+` → `+`，確實被丟掉。
- 但**字元類內** `.` 與 `+` 本來就是字面值（非萬用字元、也非量詞）。
- 以兩種寫法各測 `C4.W` / `C4-` / `C4x` / `C4` 四組樣本，結果**完全一致**。
→ 故為「看起來有意義、實際被 JS 丟掉」的**誤導性轉義**，清掉反斜線即可，零行為變更。
**教訓：靜態警告指向產生器時，先寫實測驗證行為再決定是否「修」，否則容易製造無謂的行為變更。**
**5. `eslint:recommended` 其實可用 — 前提是 globals 宣告完整**
