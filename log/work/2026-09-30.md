### 根因：90% 時間是空轉
`ui/src/modules/dataset_manager/ui/statusMessage.js` 的預設 `duration = 5000`，
而 `statusMessage.test.mjs` 前兩個案例以預設值呼叫 `showStatusMessage()` 後**未 `dispose()`**，
未清除的 `setTimeout` 吊住 Node event loop，強制等待整整 5 秒才結束。

實測佐證（直接 import 產品碼量測 event loop 存活時間）：
```
node -e 'import statusMessage.js → showStatusMessage("hello")' → held alive ms=5004
```
→ 該單檔 5167ms，佔全量 5722ms 的 **90%**；DM 子樹 149 測試的 6000ms 中有 5000ms 是空等。

### 技術深挖 (Technical Deep Dive)

**Q：為什麼不用 `--test-reporter=dot`，而是自己過濾輸出？**
`dot` reporter 輸出只有 205 字元，但**沒有 `tests/pass/fail` 摘要行**（實測輸出僅 10 行點點），
失去「一眼判斷紅綠」的能力，且失敗時無從得知哪個 case 紅。
因此 `test-related.cjs` 改採「**用預設 spec reporter 執行 → 於腳本內過濾成摘要 + 失敗明細**」。
過濾發生在子行程輸出落地**之前**，所以對話上下文只會看到約 8 行，
但保留了完整判讀能力。量測：12,439 字元 → 約 400 字元（省 95%）。

**Q：為什麼逐檔耗時都在 150ms？**
那是 Node 每啟動一個測試檔的固定成本，不是測試邏輯本身。
`node --test` 對多檔預設平行執行，故全量 34 檔只需約 1.1 秒；
但**逐檔序列執行時**這 150ms 會累加成 5.1 秒——這也是「不要逐檔跑量測」的技術理由。

**Q：`test:fast` 會不會漏測？**
會，但這正是分層的目的。契約變更（積木／產生器／i18n／主題）一定會拉進 `core_contract.test.mjs`；
純 VSIX TS／Rust／Python 異動則提示改跑 `tsc`／`cargo`／`py_compile`。
**階段收尾仍必須 `npm run test:ui`（全量）或 `npm test`（compile+lint+全量）。**
