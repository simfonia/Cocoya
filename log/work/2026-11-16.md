## 技術深挖 (Technical Deep Dive)

### 1. 序列埠「自動暫停寫入、上傳後自動續傳」的架構缺點評估

使用者提出：當 A 視窗上傳 MCU 程式時，若 B 視窗同時寫入同一個序列埠，是否能自動暫停 B 的寫入並在上傳完成後續傳？
經技術評估，此設計存在嚴重架構與教學情境缺陷：
1. **通訊語意錯亂（最嚴重）**：
   MCU 部署（deploy）伴隨韌體軟硬體重置（Reset/Reboot）與代碼刷新。B 視窗暫存的指令是針對「舊程式」的通訊協定，若在 MCU 重啟後瞬間倒灌，會干擾 bootloader/REPL 初始化或導致新程式解析崩潰。
2. **即時控制嚴重延遲（Lag）**：
   PC 端 AI 視覺（如 MediaPipe 追蹤）通常以每秒 20~30 幀高頻發送座標。MCU 燒錄耗時數秒，若將過期座標排隊暫存，重連後一口氣 flush 會造成嚴重的動作滯後。
3. **雙向握手（Request-Response）死鎖**：
   燒錄期間 MCU 無法回應 ACK，PC 端可能 timeout 或狀態機永久失步。
4. **假死與心智模型破壞**：
   B 視窗的 write() 靜默卡住，初學者會誤以為當機而強制關閉。

### 2. 為何不能單純由 Serial Hub 端主動撤銷 B 的寫入？

使用者深入詢問：若 B 視窗啟動了 webcam 並寫入 COM，此時若 Hub 主動撤銷 B 的寫入租約，B 會自動 kill 整個 Python 行程嗎？
診斷結論：**絕對不會自動 kill，且會引發嚴重的殭屍狀態**。
- `serial_hub.py` 是本機 TCP socket 伺服器，無法跨進程 kill OS 級別的 Python 子進程。
- Hub 撤銷連線只會使 B 的 `ser.write()` 拋出 `OSError`。若 B 程式有 `try...except` 或錯誤發生在背景 thread，OpenCV webcam 迴圈會繼續執行，相機持續被占用。
- B 視窗前端 UI 的執行燈號不會變回停止狀態，造成視窗狀態失步。
- 若要乾淨停止 B，必須由 Tauri 主程序（Rust 後端 `state.python_processes`）向 B 視窗執行 `stop_python`，而非單靠 Hub 斷網。

### 3. 方案二（優化明確指引）實作落地

決定維持明確互斥原則，但將提示體驗全面優化：
1. `serial_hub.py`：將 `SERIAL_WRITER_BUSY` 提示改為清晰引導：「序列埠已由另一個 Cocoya 視窗寫入；請先在該視窗點擊「停止」按鈕或關閉占用程式後再試。」
2. `deploy.rs`：精準區分 `SERIAL_WRITER_BUSY` 與一般硬體忙碌，明確提供中/英雙語指引（提示若有其他視窗執行相機/AI，先切換該視窗按「停止」）。
3. `codeRun.js`：前端攔截特定錯誤代碼，去除生硬的前綴（如 `Run failed: SERIAL_WRITER_BUSY:`），以乾淨文字直接彈出對話框。
