## 技術深挖 (Technical Deep Dive)

### 1. 均值塌陷（Mean Collapse）診斷與 Spatial Feature Head 數學原理

在舊版訓練架構中，循線任務繼承了物件偵測的骨幹與頂層設計：
```python
# 舊架構 (Legacy GAP)
x = GlobalAveragePooling2D()(backbone.output)
x = Dense(64, activation="relu")(x)
output = Dense(4, activation="sigmoid")(x)
```
- **病徵**：在包含 1,000 張循線軌跡的資料集上，不論輸入畫面中的線段在左側還是右側，模型輸出的線段座標幾乎恆為中央線段（`[0.5, 1.0, 0.5, 0.5]`），MSE 徘徊在 0.046 左右無法收斂。
- **根本原因**：MobileNetV2 輸出為 7x7x1280 特徵圖。GlobalAveragePooling2D 對每個通道做全域空間平均，將 7x7 空間維度壓縮為 1x1。此時影像的「絕對空間拓撲（線段在哪個象限）」被全域平均徹底抹除，只留下全域特徵響應強度。Dense 層無法根據平均特徵反推空間座標，最終神經網路為了降低總體 MSE 損失，退化為直接輸出資料集的統計平均值（均值塌陷）。
- **解法 (Spatial Feature Head)**：
  ```python
  # 新架構 (Spatial Head)
  x = Conv2D(64, (1, 1), activation="relu", padding="same")(backbone.output) # 保留 (7, 7, 64)
  x = Flatten()(x)                                                            # 展平成 3136 維空間向量
  x = Dense(64, activation="relu")(x)
  x = Dropout(0.2)(x)
  output = Dense(4, activation="sigmoid")(x)
  ```
  利用 1x1 卷積將通道數自 1280 降至 64，完整保留 7x7 的 49 個空間格子（每格代表影像中約 32x32 像素的原生感受野），再展平成 3136 維度，讓全連接層能夠直接感知線段端點所在的空間網格，成功破除均值塌陷。

### 2. 批次維度下的座標感知隨機水平翻轉 (Batch-level Coordinated H-Flip)

循線任務的標籤為歸一化向量 `[x1, y1, x2, y2]`。當影像水平翻轉時，幾何座標必須鏡射：
`x1_flip = 1.0 - x2, x2_flip = 1.0 - x1, y1_flip = y2, y2_flip = y1`
若單純依序對兩端點獨立做 1 - x，線段的方向向量（近端到遠端）會在翻轉時發生倒轉，因此端點 1 與端點 2 必須對調。

在初版實作中，使用 `tf.stack` 未考慮批次形狀：
```python
# 錯誤：在批次維度下 tf.stack 會將 shape (B, 4) 取片壓縮，導致 output 形狀變成 (4, 4)
flipped_line = tf.stack([1.0 - line[2], line[3], 1.0 - line[0], line[1]])
```
導致 TensorFlow 拋出 `Incompatible shapes: [4, 4] vs. [32, 4]`。
修正為支援任意批次維度（`(B, 4)`）的廣播切片與 `tf.where` 條件選擇：
```python
x1 = line[:, 0:1]
y1 = line[:, 1:2]
x2 = line[:, 2:3]
y2 = line[:, 3:4]
flipped_line = tf.concat([1.0 - x2, y2, 1.0 - x1, y1], axis=1)
condition = tf.random.uniform([tf.shape(line)[0], 1]) < 0.5
final_line = tf.where(condition, flipped_line, line)
```
每張樣本在批次內獨立以 50% 機率決定是否鏡像，且保證影像像素與幾何標籤嚴格同步。

### 3. 為什麼 val_loss < loss？驗證集是否有隨機取樣？

使用者在訓練過程中觀察到三個模式的 `loss` 與 `val_loss` 曲線呈現高度一致的下降趨勢，且 `val_loss` 全程優於 `loss`。

#### (1) 為何 val_loss 全程比 loss 低？
這在現代深度學習正規化中屬於標準且健康的行為，主因為以下三項機制的疊加：
1. **資料擴增（Data Augmentation）僅作用於訓練集**：
   - 訓練集開啟了座標感知水平翻轉、隨機亮度（max_delta=0.2）與隨機對比度（0.8~1.2），「考題變難」，模型預測難度高，故 `loss` 較高。
   - 驗證集關閉所有幾何與色彩擴增，全為無干擾的原始採集影像，「考題單純」，故 `val_loss` 自然更低。
2. **Dropout(0.2) 訓練與驗證行為差異**：
   - 訓練期間（`training=True`）隨機丟棄 20% 的神經元，強迫模型蒙眼作答，表觀 loss 上升。
   - 驗證期間（`training=False`）所有神經元 100% 啟動並縮放權重，集合全體特徵協同預測，準確率達峰值。
3. **計算時間點差異**：
   - 訓練 `loss` 是整個 Epoch 中所有批次的「動態累積平均」（包含早期權重較差時的批次）。
   - 驗證 `val_loss` 是在該 Epoch 結束時，用當前最佳權重一次性跑完全部驗證樣本。

#### (2) 驗證集是否有隨機取樣？
- **結論**：有隨機取樣，但屬於**「確定性隨機取樣（Deterministic Random Split）」**。
- **程式碼真相**：在 `common/line_dataset.py` 的 `load_line_dataset()` 中：
  ```python
  random.seed(seed) # 固定 seed=123
  random.shuffle(pairs)
  split_idx = int(len(pairs) * (1.0 - validation_split))
  train_pairs = pairs[:split_idx]
  val_pairs = pairs[split_idx:]
  ```
- 資料在切分前確實經過 `random.shuffle` 充分洗牌打亂（避免時序連拍偏差），但因為固定了亂數種子 `seed=123`，每次訓練切分出的 200 張驗證圖索引完全一致。這確保了跨架構、跨超參數測試時，驗證指標具備嚴格的客觀可比性。

### 4. 推論色彩空間對齊：OpenCV (BGR) vs MobileNetV2 (RGB)

- **問題定位**：OpenCV 透過 `cap.read()` 抓取的影格格式為 BGR。然而 MobileNetV2 預訓練權重是在 ImageNet（RGB）上訓練的，且訓練模板中的 `tf.io.decode_jpeg()` 預設解碼為 RGB。
- **影響**：推論時若未將 BGR 轉為 RGB，紅色線條與藍色線條的特徵通道會互換，導致卷積特徵響應嚴重偏離，即時推論出現抖動或無法辨識。
- **修復**：在 `ai_inference_generators.js` 生成的 `_preprocess` 輔助函式中，加入色彩空間轉換：
  ```python
  rgb = cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)
  img = cv2.resize(rgb, (self.w, self.h))
  ```
  使訓練端與推論端的影像管線達到 100% 色彩一致。
