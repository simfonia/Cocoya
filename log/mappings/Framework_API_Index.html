2. Blockly 產生器開發

2.1 使用 definitions_ 解耦定義與執行

為了解決積木擺放順序導致的 Python 語法錯誤（如先呼叫後定義），應將所有宣告型代碼放入 definitions_。

Blockly.Python.forBlock['py_function_def'] = function(block, generator) {
  const name = ...;
  const code = `def ${name}():\n  pass\n`;
  // 注入全域定義區
  generator.definitions_['func_' + name] = code;
  return null; // 該積木在當前位置不產出代碼
};
    
2.2 注入輔助函數與定義鍵命名規範


注入的 Python 函數以 `generator.definitions_[]` 存放，鍵名須唯一並具語義。例如：


Blockly.Python.forBlock['py_ai_pose_calc_angle'] = function(block, generator) {
  // math 共用 import (idempotent)
  generator.definitions_['import_math'] = 'import math';
  // 獨占鍵：三座標點求夾角 (Tuple 版)，不覆蓋 detect_punch 的 cocoya_get_angle
  generator.definitions_['func_calc_angle_3pts'] = `
def cocoya_calc_angle_3pts(a, b, c, mode='interior'):
    if not a or not b or not c: return 0
    v1x, v1y = a[0]-b[0], a[1]-b[1]
    v2x, v2y = c[0]-b[0], c[1]-b[1]
    dot = v1x*v2x + v1y*v2y
    cross = v1x*v2y - v1y*v2x
    signed = math.degrees(math.atan2(cross, dot))   # + = CCW from A->C
    if mode == 'signed': return signed
    interior = abs(signed)
    return (360 - interior) if mode == 'exterior' else interior
`;
  return ['cocoya_calc_angle_3pts(' + ptA + ', ' + ptB + ', ' + ptC + ", '" + mode + "')", Blockly.Python.ORDER_FUNCTION_CALL];
};


方向約定：正值 = 由指向 A 的射線 (BA) 逆時針旋轉到指向 C 的射線 (BC) (A→C 逆時針為正)。OpenCV 像素座標 y 軸向下，圖形上顯示方向與數學座標相反。

關係式：內角 = |signed|，外角 = 360° − 內角。詳見 docs/help/py_ai_pose_calc_angle_{zh-hant,en}.html。

    
用於將 Blockly 積木與產出代碼之間建立 1:1 對應，支援點擊積木時高亮對應程式碼行。


    
3.1 findLocatableBlock (遞迴尋找可定位父積木)

    
Frontend VSIX Tauri

    
位於 ui/src/ui/renderer.js。當使用者點擊 value/expression 積木 (具有 outputConnection) 時，
       該積木的程式碼是內嵌在父 statement 積木之中，通常沒有自己的範圍標記。此方法遞迴往上找到
       沒有 outputConnection 的 statement 積木，該積木的 ID 才會有 # S_ID/# E_ID 標記。

    
// 遞迴尋找可定位的父積木
findLocatableBlock: function(block) {
    if (!block) return null;
    if (block.outputConnection) {
        var parent = block.getParent();
        if (parent) return this.findLocatableBlock(parent);
    }
    return block;
},

// 在 syncSelection 中使用
syncSelection: function(blockId) {
    var block = Blockly.getMainWorkspace().getBlockById(blockId);
    var locatableBlock = this.findLocatableBlock(block);
    var range = this.blockToRangeMap.get(locatableBlock.id);
    // ... 高亮 range.start ~ range.end 的行 ...
};

Tauri Frontend Rust

  • Command：命令名稱。
    • 
      
  • Params (Rust, JS-passed)：前端實際傳遞者；window/state/handle 由 Tauri 自動注入，JS 不傳。
    • 
      
  • JS Invoke Keys：camelCase；Tauri 2.10.3 自動對映 snake_case↔camelCase。
      
  • Return：Rust 回傳型別。
    • 
    

    
同步規則：#[tauri::command] 簽名增改 -> 立即更新本 manifest + ui/src/bridge/{tauri,vsix}.js 呼叫端 (詳見 AGENTS.md 「Tauri 跨語言 Invoke 簽名同步規範」)。長期：引入 tauri-codegen 自動生成 typed invoke() (log/todo.md 待辦)。

來源：ui/blockly/core/blockly.js（runtime 以 register 注入 CSS；以下為實測抓出的關鍵 class 與原值）。字級應用見 log/mappings/FontScale.html。

    
/* toolbox 分類列（DOM 元素，不是 SVG） */
.blocklyToolboxDiv                     /* toolbox 容器（style.css 覆寫 z-index: 140） */
  .blocklyToolboxCategoryContainer     /* 分類項容器（margin: 1px 5px 1px 0） */
    .blocklyToolboxCategory            /* 分類列原值 height: 22px; line-height: 22px */
      .blocklyToolboxCategoryIcon      /* 16x16 sprites.png 圖示 */
      .blocklyToolboxCategoryLabel     /* 分類文字原值 font: 16px sans-serif */

/* 覆寫字級的正確寫法：提高特異度（0,2,0 勝 0,1,0），不依賴載入順序 */
.blocklyToolboxDiv .blocklyToolboxCategoryLabel { font-size: calc(16px * var(--fs-e)); }
.blocklyToolboxDiv .blocklyToolboxCategory {
    height: calc(22px * var(--fs-e));
    line-height: calc(22px * var(--fs-e));
}
    

    
三個已驗證的坑：

    
    
      
  • 積木本體（block 內文字）在 SVG 內渲染，CSS font-size 無效；只能用 Blockly.Theme 的 fontSize（Cocoya 已內建 +/- 控制項）。
    • 
      
  • Blockly 用 font 簡寫設定文字（連帶 font-size/family/weight）→ 覆寫時只寫 font-size，用 font 簡寫會把 sans-serif family 一起改掉。
    • 
      
  • .blocklyTreeLabel 為 舊版相容命名：Blockly 12.3.1 內建 CSS/DOM 完全沒有此 class（grep 命中 0 次）；主題檔沿用它是無害的防禦寫法，新規則請以 .blocklyToolboxCategoryLabel 為準。
    • 
    

    
其他：toolbox 寬度由 Blockly 於載入時量測決定 flyout 位置 → 字級改動需 reload 後量測才正確。

  
7. Cocoya 產生器管線：不可見 ID 標記（scrub_）污染陷阱（2026-09-18 除錯蒸餾）

  
症狀：放好 mcu_board_init（板名正確印出 # Board: Maker Pi RP2040 (maker-pi)），但腳位積木卻產生 # [Cocoya] 無法解析腳位: board.GP0。

  
機制（三個事實串起來）：

  
    
    
  1. ui/src/utils/generators.js 覆寫 Blockly.Python.scrub_：if (block.outputConnection) return `\u0001ID:${block.id}\u0002${code}`;——**所有具 output 連線的積木**（含陰影積木）產生的值都被前置不可見標記。
    2. 
    
  2. Blockly 核心 blockToCode 對 output 積木回傳 scrub_(block, code)，而 valueToCode 直接取用該字串（ui/blockly/core/blockly.js）→ 產生器期間拿到的腳位是 \u0001ID:c8xk...\u0002"board.GP0"。
    3. 
    
  3. hardware_generators.js 的 cocoyaResolvePinNum → CocoyaBoard.resolveGpio 只做「去引號 + 去 ^board.」→ 標記殘留 → gpioMap 查表與全板兜底掃描都 miss → null → 錯誤註解。
    4. 
  

  
為何難察覺：標記是不可見控制字元；且 ui/src/app/workspace.js 於預覽前執行 code.replace(/\u0001ID:.*?\u0002/g, '')，最終輸出與終端機都是乾淨的——只有「產生期間的語意查表」看到污染。

  
鐵律：凡產生器要對 valueToCode() 結果做語意比對（字典查表、映射、字串相等、JSON.parse）前，必須先剝除標記。

  
SSOT 實作：hardware_blocks.js → CocoyaBoard.normalizePinRef(ref)（resolveGpio 入口統一施作）；hardware_generators.js → cocoyaNormalizePinRef；mcu_car_generators.js → mcuCarNormalizePin（後兩者為顯示用，含防禦性 fallback）。

  
回歸測試：ui/src/modules/hardware/pin_resolve.test.mjs（9 測）——cd ui; node --test "src/modules/hardware/*.test.mjs"。

  
診斷手法（可重用）：以 new Function(fs.readFileSync(...)) + globalThis stub（window/Blockly）在 Node 直接載入瀏覽器模組，即可對產生器做無 GUI 的端到端測試（免開 Tauri/VSIX）。
