Cocoya 工作區還原與平台切換契約（App 層）

建立日期：2026-09-22（Input "RESULT" doesn't exist on "py_ai_get_line_end" 除錯蒸餾）。適用範圍：ui/src/app/*.js（persistence / lifecycle / workspace / config）與其後端來源（Rust file.rs、VSIX fileOps.ts / cocoyaManager.ts）。

1. 三條「XML → 工作區」路徑（都必須先切平台）

路徑XML 來源平台來源順序狀態

其他 domToWorkspace 呼叫點（workspace.js 的 minimap 重建）只在同平台內複製，無此問題。

2. 鐵律：載入積木前必須先切換平台

模組依平台載入（ui/src/core_manifest.json 的 platforms；如 ai_inference 僅 ["PC"]，mcu_* 僅 ["MicroPython"]）。 未載入的積木型別被 Blockly 建立時，只會得到 Blockly.Blocks[type] === undefined：Blockly 印一行 Block definiton for xxx not found 警告後，建立一個「空積木」（無 input／無 field），且不會拋錯。

空積木本身不致命，致命的是「之後平台被切換、產生器被註冊」——此時 workspaceToCode 會呼叫產生器，而產生器讀不到的 input／field 就爆：

ReferenceError: Input "RESULT" doesn't exist on "py_ai_get_line_end"
ReferenceError: Python generator does not know how to generate code for block type "xxx"

兩者都指向同一根因：建立積木的當下，該型別沒有註冊。
⚠️ 2026-09-22 Round 2 補正：本案例的真正根因其實是另一條同症狀路徑——模組 i18n 的 AI_GET_LINE_END 訊息缺 %1（args0 有 RESULT＋END 兩個 arg），init() → jsonInit → validateTokens 拋 Message does not reference all 2 arg(s)，積木一樣變成無 input 的半成品。判讀準則：看到 Message does not reference all N arg(s) ＝ i18n 佔位符與 args 不對齊；Input "..." doesn't exist 只是它的下游症狀。回歸測試：block_jsoninit.test.mjs。

SSOT 實作：CocoyaApp.ensurePlatformForXml(dom)（ui/src/app/persistence.js） ——讀 XML 的 platform 屬性，與 currentPlatform 不同才 await setPlatformUI(platform)； 屬性缺失／傳 null 靜默略過。任何新的 XML 還原入口都必須先呼叫它（loadWorkspace 已有等價邏輯）。

// 正確樣板（以 checkAutoBackup 為例）
const dom = Blockly.utils.xml.textToDom(backupXml);
await this.ensurePlatformForXml(dom);   // ★ 先切平台（載入該平台模組與產生器）
Blockly.Events.disable();
try {
    this.workspace.clear();
    Blockly.Xml.domToWorkspace(dom, this.workspace);
} finally { Blockly.Events.enable(); }
this.triggerCodeUpdate();

3. 為何平台會與專案不符（currentPlatform 的來源）

  • config.js：currentPlatform = localStorage['cocoya_platform'] || 'MicroPython'（預設 MicroPython）。
  • localStorage 是依 origin 隔離：Tauri 開發（vite localhost:5173）與 Tauri 打包（http://tauri.localhost）各有自己的 cocoya_platform；多視窗共用同一份（另一視窗切平台會改到你的值，但自己記憶體中的 currentPlatform 不會跟著變）。
  • 啟動備份／專案旁 .bak 是跨 session 殘留的檔案 → 其 platform 與本次啟動的 currentPlatform 完全獨立，不能假設一致。
  • 診斷手法：%LOCALAPPDATA%\com.cocoya.app\EBWebView\Default\Local Storage\leveldb\*.log 可直接看到 cocoya_platform 的歷次寫入值（檔案被執行中的 App 鎖住，需以 ReadWrite 共享模式開啟）。

7. 待辦 / 注意

  • 使用者若已把「空積木」存進專案，該積木的 field 值無法救回（開啟後需重設，下拉會停在第一項）。
  • setPlatformUI 的 toolbox 重建為 fire-and-forget（updateToolbox 同步；搜尋索引 500ms 後重建），與平台正確性無關；但呼叫端若要緊接著載入積木，必須 await。
  • 專案是否可用「目前平台」開啟，仍屬使用者選擇（例如刻意在 MicroPython 平台開 PC 專案）；此時由 _describeCodegenError 給出可讀提示，而非靜默失敗。
